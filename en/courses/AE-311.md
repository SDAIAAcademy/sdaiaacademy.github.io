## Description

Participants practise the engineer's part in deciding what to build. In a role-played engagement with a fictional regional water utility that asks for an AI assistant for leak reports, they interview call-centre and field staff about what happened last week, map the workflow and its exceptions, choose and reject use cases, write the specification as the main deliverable with acceptance criteria as evaluation cases, test the riskiest assumption with a thin prototype built with a coding agent, cost the value case, brief the utility's leadership and hand over a system the utility's own team can run.

## Learning outcomes

By the end, the participant can:

- Analyse a requested AI use case through interviews about past behaviour and a workflow map, and restate the problem where the evidence differs from the request.
- Draft a specification with users, non-goals, constraints, data classification and acceptance criteria written as evaluation cases.
- Test the riskiest assumption with a thin prototype and role-played user sessions.
- Build a value case with cost per successful task, ranges for uncertain inputs and a break-even point, and decide whether to proceed.
- Deliver a recommendation and a hand-over package to non-technical leadership and the receiving team.

## Topics

### Discovery

- Interviews about past behaviour

### Specification as the deliverable

- Problem, users and non-goals
- Acceptance criteria as evaluation cases

- Riskiest assumption first
- Reversible and irreversible choices
- Decision records

### Value and communication

- Cost per successful task and break-even
- Ranges instead of point estimates
