AE-404

Harness Engineering for Long-Running and Multi-Agent Systems

  • Level 400 · Evaluate
  • Intensive
  • 5 days · 26 h
  • Available

Participants design and measure harnesses for agents that run for an hour or more, hand work between roles and keep memory across sessions. For a fictional national library's digitisation unit, whose agents build small catalogue services from specifications checked by hidden acceptance tests, they separate planner, generator and evaluator roles, design memory that writes, consolidates, retrieves and forgets, steer asynchronous subagents, and make sessions survive crashes and approval pauses. On scaled-down tasks they hold the model fixed and remove harness components one at a time to find which still pay.

Who it is for

Audience: specialist

Engineers who have completed the level 300 core or can show equivalent work: a production AI system they built, operated and can defend.

Learning outcomes

By the end, the participant can:

  1. Applied

    Implement planner, generator and evaluator roles that exchange work through files and stop on completion criteria agreed before work.

  2. Performance

    Design a memory layer that writes, consolidates, retrieves and forgets, guarding against stale notes and concurrent overwrites.

  3. Performance

    Build an orchestrator that steers asynchronous subagents and receives summaries rather than transcripts.

  4. Performance

    Build durable sessions with an event log kept apart from the harness, idempotent tools and a human approval pause before irreversible actions.

  5. Performance

    Evaluate harness components by ablation with the model held fixed, reporting success over repeated trials, cost and time per accepted task.

  6. Performance

    Review a harness design and decide between a single agent with subagents and a multi-agent design on measured coordination cost.

Format and days

  4. Day 4 Measure the harness, then decide

    1. Ablation with the model held fixed
    2. Repeated trials and intervals
    3. Retesting after a model change
    4. Harness design review

  5. Day 5 Capstone project presentations

More about this course

Topics

Long runs and role separation

  • Premature wrap-up and self-praise
  • Planner, generator and evaluator
  • Completion criteria agreed before work
  • When a separate evaluator pays

Context and memory

  • Compaction against reset with hand-off files
  • Subagents return summaries, not transcripts
  • Write, consolidate, retrieve, forget
  • Stale notes and concurrent writers

Asynchronous and multi-agent work

  • Steer, queue and notify
  • Orchestrator-worker, pipeline and peer topologies
  • Cascading failures and coordination cost

Durable sessions

  • Session log, harness and sandbox as replaceable parts
  • Resuming from the event log
  • Pausing for human approval
  • Idempotency keys and compensation

Harness ablation

  • Holding the model fixed
  • Repeated trials and intervals
  • Retesting after a model upgrade
  • The harness as a versioned product

Tools and platforms

These are examples. Any equivalent tool may be used instead.

Language model access
a hosted open-weight model on a call budget, a locally served open-weight model, any commercial API
Harness base
a hand-written loop in Python, goose, OpenCode
Memory store
Markdown files under version control, SQLite
Durable execution and event log
an append-only log in SQLite, Temporal, LangGraph checkpoints
Traces
OpenTelemetry with Langfuse, Arize Phoenix
Evaluation harness
Inspect, pytest with outcome graders
Execution sandbox
Docker or Podman containers, OpenSandbox

How the work is assessed

  • Supervised entry and exit checks, AI-off: name the failure in a transcript excerpt, compute consistency over three trials, choose between compaction and reset (20%)
  • Capstone rubric: harness and hand-offs 20, memory and durability tests 20, ablation and statistics 30, design record 15, reproducibility 15 (60%)
  • Live defence (20%)
To pass
70% overall and at least 60% on both the capstone rubric and the supervised check

Use of AI in the course

AI-off for the supervised checks. AI-tutor in the labs: it explains traces and framework behaviour but does not write harness components. AI-full in the capstone, coding agents included, with transcripts kept and the design defended live.

AI-off: no AI assistance. AI-tutor: an assistant that hints and explains but does not give the answer. AI-full: any assistance; the participant owns the result and defends it.
