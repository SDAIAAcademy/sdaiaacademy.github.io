DEV-AGT-403 Agent System Design Reviews

  • Level 400 · Evaluate
  • Studio
  • 30 h
  • Audience: specialist

Track

AI Engineering

Stream

DEV-AGT Agentic Systems

Level

Level 400 · Evaluate

Audience

specialist

Format

Studio: six weeks part-time of coached review rounds, ending in a written review and a panel defence

Total hours

30 h

Prerequisites

  • DEV-AGT-301 Agentic Systems Engineering: Loops, Context and Harnesses
  • Has completed DEV-AGT-401 or DEV-AGT-402, or has shipped an agent system to real users
  • Writes a structured technical document such as an architecture decision record

Description

Participants review agent system designs the way an architecture board should: first asking whether an agent is needed at all, then setting the autonomy level, tracing failure and cost, and writing a review the design owner can act on. In coached rounds on design dossiers built from public engineering write-ups and synthetic proposals, each participant reviews several designs with peers, then leads a full written review of one design and defends it before a panel that includes an experienced agent engineer.

Learning outcomes

By the end, the participant can:

  1. Performance

    Decide whether a proposed system needs an agent, a fixed workflow or no model at all, from the task's environment, context and verifiability.

    Given a design dossier and its business case.

    Evidence a decision section in the written review with the cheaper alternative costed.

  2. Performance

    Evaluate a design's autonomy level, task horizon, persistent state and authority, and set human oversight proportionate to the risk.

    Given the dossier and the sponsor's stated risk tolerance.

    Evidence an autonomy and oversight table naming each approval point and the evidence that it is not ceremonial.

  3. Performance

    Diagnose likely failure modes and compounding risks using a published agentic failure taxonomy and risk list.

    Given the design and three incident reports from comparable systems.

    Evidence a failure analysis ranked by likelihood and impact, with a control or test for each item.

  4. Performance

    Evaluate the cost of a design per accepted task, including retries, reasoning tokens, cache behaviour and human review time.

    Given traffic assumptions and published price sheets.

    Evidence a cost model with a sensitivity analysis on the two most uncertain inputs.

  5. Performance

    Review the evaluation and release plan of a design for outcome grading, consistency over trials and regression gates.

    Given the design's evaluation plan.

    Evidence review findings with concrete tests the design owner must add.

  6. Performance

    Defend a written design review before a panel and revise it in response to challenge.

    Given a 30-minute panel session.

    Evidence the final review, the panel scoring sheet and a change log of revisions.

Topics

The design review as a practice

  • Review versus approval
  • Roles: owner, reviewer, panel
  • Decision records
  • Writing findings the owner can act on

Is an agent needed

  • Fixed workflow, agent or deterministic code
  • Environment, context and verifiability as predictors
  • The task contract: goal, environment, permitted actions, observations, completion criteria

Autonomy and oversight

  • Levels of autonomy
  • Horizon, state and authority as exposures
  • Risk-tiered human oversight
  • Approval theatre and fatigue
  • Kill switches and escalation paths

Failure analysis

  • Agentic failure taxonomies
  • Compounding error over many steps
  • Goal hijack, tool misuse and privilege abuse
  • Memory poisoning and cascading failures
  • Recovery paths

Cost and capacity

  • Cost per accepted task, not per token
  • Token mix: cache reads, reasoning, retries
  • Model tiering and routing
  • Latency budgets
  • Energy use of agentic workloads

Evidence a design must bring

  • Evaluation plans and consistency metrics
  • Harness ablation evidence
  • Containment and identity evidence
  • Operational readiness and runbooks

Governance fit

  • Data classification and personal data
  • Documentation of tool access and operational limits
  • Accountability for agent actions
  • Mapping a design to a risk management framework

Tools and platforms

These are examples. Any equivalent tool may be used instead.

Architecture diagramming as code
Mermaid, PlantUML, Structurizr
Cost modelling
a spreadsheet, a Python notebook
Shared review documents with version history
Markdown in a Git repository, any collaborative editor with history
Risk and failure catalogues
Open Worldwide Application Security Project (OWASP) Top 10 for Agentic Applications, OWASP Model Context Protocol (MCP) Top 10, in beta, MITRE ATLAS

How the work is assessed

  • Supervised check without AI assistance: triage three unseen proposals in 45 minutes (10%)
  • Review rounds and peer reviews (30%)
  • Capstone written review scored on a six-criterion rubric (40%)
  • Panel defence (20%)
To pass
70% overall and a pass from the panel

Use of AI in the course

AI-off for the supervised triage check and the panel. AI-tutor during review rounds. AI-full for research and drafting the capstone review, which the participant owns, discloses and defends.

AI-off: no AI assistance. AI-tutor: an assistant that hints and explains but does not give the answer. AI-full: any assistance; the participant owns the result and defends it.
