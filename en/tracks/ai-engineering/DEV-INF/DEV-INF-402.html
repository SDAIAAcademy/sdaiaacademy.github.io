DEV-INF-402 Scaling Machine Learning Systems: Distributed Training and Fleets

  • Level 400 · Evaluate
  • Intensive
  • 36 h
  • Audience: specialist

Track

AI Engineering

Stream

DEV-INF Infrastructure, Performance and Architecture

Level

Level 400 · Evaluate

Audience

specialist

Format

Intensive: 4 teaching days and a capstone day, with guided pre-work and a tracked follow-up task

Total hours

36 h

Prerequisites

  • DEV-INF-201 Machine Learning Systems on One Machine
  • DEV-MLE-202 Deep Learning Engineering
  • Debugs a training loop and reads its memory use
  • Explains network bandwidth, latency and topology

Description

Participants time collective communication and fit a cost model to it, train a small transformer with replicated and then sharded state across worker processes, plan data, tensor and pipeline parallelism for a large model and check the plan in a simulator, set checkpoint intervals from failure rates, and diagnose low utilisation in recorded fleet telemetry. Labs run on CPU workers, a provided multi-accelerator node for one session, and an analytical simulator.

Learning outcomes

By the end, the participant can:

  1. Applied

    Compute collective communication time with a latency-bandwidth model and calibrate it against measurements.

    Given timings from four to sixteen workers on CPU and on the provided node.

    Evidence a calibrated model and its error on a held-out worker count.

  2. Performance

    Build a training run with replicated, then sharded, model and optimiser state and measure scaling efficiency.

    Given a small transformer and a public text corpus.

    Evidence run logs, memory per worker and a scaling curve with its losses explained.

  3. Performance

    Design a parallelism plan that fits device memory and maximises throughput for a large model.

    Given a model of tens of billions of parameters and a cluster with scale-up and scale-out links.

    Evidence memory per device, communication per step, pipeline bubble and predicted step time, checked in the simulator.

  4. Performance

    Design a checkpoint and recovery policy from failure rates and checkpoint cost.

    Given fleet failure statistics and a job's state size.

    Evidence a calculated interval and a fault-injection run that resumes within the lost-work budget.

  5. Performance

    Diagnose the causes of low accelerator utilisation in a fleet.

    Given recorded telemetry with seeded stragglers, input stalls and network contention.

    Evidence a report ranking causes by lost throughput, with evidence and fixes.

  6. Performance

    Evaluate fleet serving options for several models across two sites.

    Given a multi-model demand trace and an availability target.

    Evidence a fleet plan with cost, utilisation and availability, tested against one failure scenario.

Topics

The fleet and its limits

  • Memory capacity and bandwidth
  • Scale-up and scale-out interconnects
  • Amdahl's law and the communication tax

Collective communication

  • All-reduce, all-gather, reduce-scatter, all-to-all
  • Ring and tree algorithms
  • Overlapping communication with computation

Distributed training

  • Data parallelism and sharded optimiser state
  • Tensor, pipeline and expert parallelism
  • Mixed precision and activation recomputation
  • Planning with a simulator

Fault tolerance

  • Failure models and silent data corruption
  • Checkpoint intervals and the Young-Daly rule
  • Elastic restart and lost-work budgets

Fleet efficiency and serving at scale

  • Utilisation, stragglers and input stalls
  • Job queues and gang scheduling (mechanics in DEV-INF-301)
  • Placement across sites and failover
  • Energy and carbon of training and serving

Tools and platforms

These are examples. Any equivalent tool may be used instead.

Distributed training library
PyTorch distributed, DeepSpeed, JAX
Communication backend
Gloo on CPU, NCCL on GPUs, MPI
Analytical simulator
MLSys·im, a spreadsheet cost model
Distributed job runner
Slurm, Ray, Kubeflow Trainer
Profiling and telemetry
PyTorch profiler, Prometheus
Compute
CPU worker processes on a laptop, a provided multi-accelerator node

How the work is assessed

  • Supervised check without AI assistance: memory and communication estimates for two plans (10%)
  • Graded labs (30%)
  • Capstone on a six-criterion rubric (45%)
  • Live defence (15%)
To pass
70% overall and at least 60% on the capstone rubric, with every number traceable to a calculation, measurement or simulator run

Use of AI in the course

AI-off for the supervised check and the hand calculations in labs 1 and 3; AI-tutor in the other labs; AI-full in the capstone, which is defended live.

AI-off: no AI assistance. AI-tutor: an assistant that hints and explains but does not give the answer. AI-full: any assistance; the participant owns the result and defends it.
