DEV-INF-301 Container Orchestration for AI Workloads: Accelerators, Scheduling and Autoscaling

  • Level 300 · Develop
  • Intensive
  • 36 h
  • Audience: practitioner

Track

AI Engineering

Stream

DEV-INF Infrastructure, Performance and Architecture

Level

Level 300 · Develop

Audience

practitioner

Format

Intensive: 4 teaching days and a capstone day, with guided pre-work and a tracked follow-up task

Total hours

36 h

Prerequisites

  • DEV-OPS-201 Deploying AI Services: Containers, Serving and Monitoring
  • Writes and applies declarative manifests on a container orchestrator
  • Explains time to first token and throughput for a language model service

Description

Participants run AI workloads on a shared container cluster as a platform team must: accelerators allocated and shared safely, training jobs admitted fairly under quotas, distributed jobs placed all at once, and inference services scaled and routed on the metrics users feel. Labs use single-node clusters on provided virtual machines with simulated accelerators, small open-weight models and recorded traces, with the public Kubernetes AI conformance checklist as the rubric.

Learning outcomes

By the end, the participant can:

  1. Applied

    Configure accelerator allocation for whole, shared and partitioned devices and verify isolation between tenants.

    Given a cluster with a simulated device driver and two tenants.

    Evidence manifests and a test run showing correct devices and no cross-tenant access.

  2. Applied

    Configure queue-based admission with quotas, borrowing, priorities and preemption for a shared accelerator pool.

    Given a synthetic week of jobs from three teams.

    Evidence a replay report of utilisation, wait time and share per team against the policy.

  3. Applied

    Implement gang scheduling so that a multi-worker training job no longer holds accelerators idle.

    Given two competing jobs that deadlock under the default scheduler.

    Evidence event logs before and after, with idle accelerator-minutes.

  4. Performance

    Design autoscaling for an inference service on queue or latency metrics, including scale to zero and a cold-start budget.

    Given a recorded trace with a burst, a latency objective and a cost ceiling.

    Evidence a replay comparing goodput and accelerator-hours with a fixed-replica baseline.

  5. Performance

    Evaluate load-aware and prefix-cache-aware routing against round-robin.

    Given several small-model replicas and a shared-prefix workload.

    Evidence a comparison of latency percentiles and cache hit rate with a recommendation.

  6. Performance

    Audit a cluster against a public AI conformance checklist and deliver a ranked remediation plan.

    Given a provided cluster with seeded gaps.

    Evidence automated test evidence for every mandatory item and a plan the assessor can re-run.

Topics

Accelerators as cluster resources

  • Device plugins versus dynamic resource allocation
  • Time-slicing, partitioning and virtualised devices
  • Device health, taints and driver operators

Admission and scheduling

  • Queues, quotas, cohorts and borrowing
  • Preemption with checkpoint and resume; dominant-resource fairness
  • Gang and topology-aware placement

Serving and autoscaling

  • Serving operators and model weights as registry artefacts
  • Cold start and scale to zero
  • Scaling pods on service-objective metrics, nodes by accelerator type

Inference-aware traffic

  • Gateway inference extensions and endpoint picking
  • Priority, fairness and load shedding
  • Prefill and decode placement (depth in DEV-INF-401)

Observability, isolation and conformance

  • Per-accelerator metrics in a standard format
  • Mediated device access and workload sandboxing
  • Showback of accelerator-hours per tenant
  • The checklist as an acceptance test

Tools and platforms

These are examples. Any equivalent tool may be used instead.

Local cluster with simulated accelerators
kind or k3d, a dynamic resource allocation example driver, KWOK
Batch admission and scheduling
Kueue, KAI Scheduler, Volcano
Serving control plane and engine
KServe, llm-d, vLLM, llama.cpp server
Autoscaling
Horizontal Pod Autoscaler with custom metrics, KEDA
Inference-aware gateway
Gateway API Inference Extension endpoint picker, llm-d inference scheduler, Agent Router (formerly Envoy AI Gateway)
Metrics
Prometheus, OpenTelemetry Collector

How the work is assessed

  • Supervised scheduling check without AI assistance (15%)
  • Graded labs (35%)
  • Capstone audit and configuration (40%)
  • Design review defence (10%)
To pass
70% overall, every mandatory checklist item evidenced, and at least 60% on the supervised check

Use of AI in the course

AI-off for the supervised scheduling check. AI-tutor in labs, including for manifests. AI-full in the capstone, where each participant defends every configuration live.

AI-off: no AI assistance. AI-tutor: an assistant that hints and explains but does not give the answer. AI-full: any assistance; the participant owns the result and defends it.
