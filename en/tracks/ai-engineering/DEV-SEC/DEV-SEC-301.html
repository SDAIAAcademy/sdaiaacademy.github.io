DEV-SEC-301 Securing Language Model and Agent Applications

  • Level 300 · Develop
  • Intensive
  • 36 h
  • Audience: practitioner

Track

AI Engineering

Stream

DEV-SEC Security and Privacy Engineering for AI

Level

Level 300 · Develop

Audience

practitioner

Format

Intensive: 4 teaching days and a capstone day, with guided pre-work and a tracked follow-up task

Total hours

36 h

Prerequisites

  • DEV-SEC-201 Secure Development of AI Applications
  • Has built an agent that calls tools in a loop (DEV-AGT-301 or equivalent)
  • Runs containers locally

Description

Participants attack, then defend, a synthetic procurement agent that reads supplier email, searches documents, keeps memory and acts through Model Context Protocol (MCP) servers. They threat-model it, run injection and exfiltration attacks, then contain it with a sandbox and egress allowlist, scoped delegated tokens, hardened protocol servers, measured guardrails and well-placed approvals. Platform isolation and identity are DEV-AGT-402; red-team programmes are DEV-SEC-302.

Learning outcomes

By the end, the participant can:

  1. Applied

    Prepare a threat model naming trust boundaries, private data, untrusted inputs and exit paths.

    Given the agent's architecture and tools.

    Evidence a data-flow diagram and threat table mapped to risk-list entries.

  2. Applied

    Test the agent against injection and exfiltration through documents, images, links and tool arguments.

    Given an attack set and poisoned documents.

    Evidence an attack log with success rates over repeated trials.

  3. Performance

    Design containment that removes private data, untrusted content or the exit path from each high-risk flow.

    Given the threat model and a container runtime.

    Evidence a configuration and a re-run showing which attacks now fail.

  4. Performance

    Build delegated authorisation with scoped, short-lived tokens exchanged at each hop.

    Given a local identity provider and two protocol servers.

    Evidence tests proving a stolen token cannot exceed its scope or audience.

  5. Applied

    Measure guardrails on attack and benign sets and set thresholds.

    Given labelled sets in Arabic and English.

    Evidence a memo with detection and false-refusal rates.

  6. Performance

    Evaluate the residual risk of a hardened agent and decide which actions still need approval.

    Given another team's agent and attack results.

    Evidence a findings report defended live.

Topics

Threat modelling agents

  • Trust boundaries, data flows and STRIDE applied to agents
  • Private data, untrusted content and exit paths
  • Risk lists and adversary technique mapping

Injection and exfiltration

  • Direct, indirect and cross-modal injection
  • Exfiltration through permitted paths
  • Memory and retrieval poisoning

Containment and authorisation

  • Sandboxes for generated code
  • An egress allowlist is a capability grant
  • Token exchange, audience, scope and lifetime
  • Forbidden token passthrough and the confused deputy

Protocol servers and tools

  • Tool poisoning and changes after approval
  • Hostile text in tool results
  • Request forgery during metadata discovery
  • Local, shadow and over-scoped servers

Guardrails, approvals and audit

  • Classifier error rates and false refusals
  • Approval fatigue
  • Action logs for investigation

Tools and platforms

These are examples. Any equivalent tool may be used instead.

Locally served open-weight models
Ollama, vLLM, llama.cpp
Protocol server code
official MCP SDKs, plain function-calling tools
Sandbox with egress control
Podman, Docker, gVisor
Identity provider with token exchange
Keycloak, any OAuth 2 provider in a container
Guardrails
an open-source guardrail framework, an open-weight safety classifier
Attack tooling
garak, PyRIT, promptfoo
Risk references
OWASP GenAI Security Project lists, MITRE ATLAS

How the work is assessed

  • Supervised check: threat-model an unseen design (20%)
  • Labs (30%)
  • Capstone report and defence (50%)
To pass
70% overall and at least 60% on the capstone

Use of AI in the course

AI-off in the supervised check; AI-tutor in labs; AI-full on the red-team day, with assistant-generated attacks and fixes logged and defended.

AI-off: no AI assistance. AI-tutor: an assistant that hints and explains but does not give the answer. AI-full: any assistance; the participant owns the result and defends it.
