DEV-SEC-201 Secure Development of AI Applications

  • Level 200 · Apply
  • Workshop
  • 16 h
  • Audience: practitioner

Track

AI Engineering

Stream

DEV-SEC Security and Privacy Engineering for AI

Level

Level 200 · Apply

Audience

practitioner

Format

Workshop: two days with labs and a hardening project

Total hours

16 h

Prerequisites

  • Has built a small language model application with a tool, in Python with tests and Git

Description

Participants make an insecure helpdesk assistant, with retrieval over synthetic policy documents and two tools, fit to ship. They map its weaknesses to public risk lists, treat model output as untrusted input, keep secrets server-side, scan dependencies and model files, carry each user's permissions into retrieval and log without personal data. Injection in depth is DEV-SEC-301; testing agent-written code is DEV-SWE-204.

Learning outcomes

By the end, the participant can:

  1. Awareness

    Distinguish risks of the model as a component from risks of the model as an agent.

    Given twelve incident descriptions.

    Evidence a mapping to risk-list entries with at least ten of twelve correct.

  2. Applied

    Implement validation and encoding of model output before it reaches a query, a web page or a shell.

    Given three seeded exploit payloads.

    Evidence tests that block each payload.

  3. Applied

    Configure secret handling so that no key appears in prompts, client code, logs or history.

    Given a repository with planted secrets.

    Evidence a clean scan and a hook that blocks a new key.

  4. Applied

    Apply document-level access control to retrieval.

    Given a corpus with three classification levels and four roles.

    Evidence an access test matrix that passes for every role.

  5. Performance

    Review a small AI application and decide whether it may ship.

    Given an unseen application.

    Evidence a findings list with fixes and a defended ship decision.

Topics

Risk vocabulary

  • Public risk lists for language model and agentic applications
  • Why injection has no model-level fix

Inputs and outputs

  • Output as untrusted input
  • Schema validation and context encoding
  • Unbounded consumption and rate limits

Secrets, permissions and dependencies

  • Server-side keys and secret stores
  • User permissions carried into retrieval
  • Pinned dependencies and invented package names
  • Unsafe model file formats

Logging

  • Security events worth logging
  • Redacting personal data

Tools and platforms

These are examples. Any equivalent tool may be used instead.

Language model access
a locally served open-weight model, any OpenAI-compatible API
Code and secret scanning
Semgrep, Gitleaks, TruffleHog
Dependency and model-file scanning
OSV-Scanner, Trivy, ModelScan
Continuous integration
GitLab CI, GitHub Actions

How the work is assessed

  • Supervised practical: fix two flaws in a code sample (30%)
  • Labs (30%)
  • Capstone and review (40%)
To pass
60% overall, with both supervised flaws fixed

Use of AI in the course

AI-off in the supervised practical; AI-tutor in labs; AI-full in the capstone, defended live.

AI-off: no AI assistance. AI-tutor: an assistant that hints and explains but does not give the answer. AI-full: any assistance; the participant owns the result and defends it.
