DEV-EVL-301 Evaluation-Driven Development for Language Model Applications

  • Level 300 · Develop
  • Intensive
  • 28 h
  • Audience: practitioner

Track

AI Engineering

Stream

DEV-EVL Evaluation and Quality Engineering for AI Systems

Level

Level 300 · Develop

Audience

practitioner

Format

Intensive: 4 teaching days and a capstone day, with guided pre-work and a tracked follow-up task

Total hours

28 h

Prerequisites

  • Has called a language model API from Python and parsed a structured response
  • Reads a confusion matrix and computes precision and recall

Description

Participants learn to treat evaluation as the specification of a language model application. They read traces of a working but unreliable assistant, name its failure modes, turn them into code-based checks and calibrated model-graded checks, and wire the suite into a regression gate. The course uses one synthetic case study from start to finish, and every number a participant reports comes from a run they executed.

Learning outcomes

By the end, the participant can:

  1. Awareness

    Distinguish code-based checks, model-graded checks and human review, and state when each is the cheapest reliable instrument.

    Given six described failure modes of a support assistant.

    Evidence a completed decision table that matches the reference answer on at least five of six rows.

  2. Applied

    Carry out open and axial coding of application traces to produce a failure taxonomy with counts.

    Given 100 traces from the case-study assistant.

    Evidence a taxonomy file with at least five named failure modes, each with a definition, three example trace ids and a frequency.

  3. Applied

    Implement code-based evaluators for structure, grounding and policy rules.

    Given the failure taxonomy and a provided harness.

    Evidence a test suite that runs unattended and reports pass rates per failure mode.

  4. Applied

    Calibrate a model-graded evaluator against human labels and report its agreement with a confidence interval.

    Given 60 human-labelled examples split into development and held-out sets.

    Evidence a calibration report with true-positive and true-negative rates on the held-out set.

  5. Performance

    Decide between two candidate configurations of an application using a statistically sound comparison.

    Given an evaluation suite, a fixed budget of model calls and a stated minimum effect of interest.

    Evidence a one-page decision memo with the comparison, its uncertainty, cost and latency, and the decision.

  6. Performance

    Build a regression gate that blocks a change when a critical failure mode gets worse.

    Given a repository with continuous integration and the evaluation suite.

    Evidence a pipeline run that passes on the baseline and fails on a seeded regression, with the run logs.

Topics

Why evaluation is the specification

  • Non-determinism and the three gulfs between intent, prompt and behaviour
  • Benchmarks versus application evaluations
  • What leaderboards do and do not tell you

Error analysis

  • Collecting and sampling traces
  • Open coding and axial coding
  • Failure taxonomies and saturation
  • Prioritising by frequency and severity

Evaluators

  • Assertions and reference-based metrics
  • Model-graded checks: binary criteria over rating scales
  • Calibrating a grader against human labels
  • Correcting observed pass rates for grader error

Comparing systems

  • Paired comparisons and bootstrap intervals
  • Sample size and minimum effect of interest
  • Cost, latency and quality as one decision

Evaluation in the delivery pipeline

  • Golden sets, versioning and data leakage
  • Regression gates in continuous integration
  • From offline suites to online monitoring
  • Human review queues

Responsible evaluation

  • Subgroup and language slices, including Arabic and English
  • Privacy of traces and labelled data
  • Documenting limits in a system card

Tools and platforms

These are examples. Any equivalent tool may be used instead.

Language model access through an OpenAI-compatible endpoint
a hosted open-weight model, a locally served open-weight model, any commercial API
Evaluation harness
Inspect, promptfoo, pytest with custom assertions
Trace store and viewer
Langfuse, Arize Phoenix, OpenTelemetry with a notebook viewer
Statistics
SciPy, statsmodels
Continuous integration
GitHub Actions, GitLab CI

How the work is assessed

  • Graded labs (40%)
  • Capstone repository scored on a five-criterion rubric (50%)
  • Oral defence of one design decision (10%)
To pass
70% overall and at least 60% on the capstone rubric

Use of AI in the course

AI-off for the supervised check of fundamentals (reading a confusion matrix, computing agreement by hand). AI-tutor in the labs. AI-full in the capstone, which the participant defends live.

AI-off: no AI assistance. AI-tutor: an assistant that hints and explains but does not give the answer. AI-full: any assistance; the participant owns the result and defends it.
