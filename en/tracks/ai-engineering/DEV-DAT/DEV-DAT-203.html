DEV-DAT-203 Streaming and Change Data Capture

  • Level 200 · Apply
  • Intensive
  • 30 h
  • Audience: practitioner

Track

AI Engineering

Stream

DEV-DAT Data Engineering and Architecture

Level

Level 200 · Apply

Audience

practitioner

Format

Intensive: 4 teaching days and a capstone day, with guided pre-work and a tracked follow-up task

Total hours

30 h

Prerequisites

  • DEV-DAT-201 Modern Data Engineering
  • Runs multi-service applications with containers on a laptop
  • A laptop with about 16 GB of memory for the container stack, or a provided remote workspace

Description

Participants build the event backbone of a fictional delivery company. They publish order and courier events to a partitioned log, capture changes from the payments database without touching its code, and process both streams with event-time windows, watermarks and keyed state. They make the pipeline survive crashes and duplicate deliveries without double counting, write results into an open table format and serve a low-latency view in streaming SQL. Generators replay synthetic events, some late, out of order or duplicated.

Learning outcomes

By the end, the participant can:

  1. Awareness

    Distinguish logs from queues and the three delivery guarantees, and state what each costs.

    Given five described integration needs.

    Evidence a choice table matching the reference on four of five.

  2. Applied

    Configure a partitioned log with keys, schemas and consumer groups that preserve per-entity ordering.

    Given order and courier producers.

    Evidence consumer output showing per-key order under parallel consumers.

  3. Applied

    Implement log-based change data capture, including deletes and schema changes.

    Given a payments database under synthetic load.

    Evidence a change stream whose replay reproduces the source table.

  4. Applied

    Implement event-time windows with watermarks and keyed state, and compare them with a batch recomputation.

    Given a replay with late and out-of-order events.

    Evidence results within the stated tolerance.

  5. Performance

    Build a stream into an open table format that loses and duplicates nothing after a crash.

    Given an injected crash and duplicate redelivery.

    Evidence matching counts and checksums after recovery, with run logs.

  6. Performance

    Decide between streaming, micro-batch and batch from latency, cost and correctness evidence.

    Given three business requests and the measured pipeline.

    Evidence a decision record defended in the capstone.

Topics

Logs, queues and events

  • Partitions, keys, offsets and retention
  • Consumer groups and queue semantics
  • Event schemas and compatibility rules

Change data capture

  • Log-based versus query-based capture
  • Snapshots, deletes and schema changes
  • The outbox pattern

State and time

  • Event time versus processing time
  • Windows, watermarks and late data
  • Keyed state and checkpoints
  • Joining streams with tables

Correctness under failure

  • End-to-end delivery guarantees
  • Idempotent sinks and transactional writes
  • Consumer lag, back-pressure and dead-letter topics
  • Replays and reprocessing

Streams into tables and SQL

  • Streaming into open table formats; compacting small files
  • Incrementally maintained views
  • Latency budgets and running cost

Tools and platforms

These are examples. Any equivalent tool may be used instead.

Distributed log
Apache Kafka, a Kafka-compatible broker
Change data capture
Debezium, database-native logical replication
Event schemas with a compatibility-checking registry
Apache Avro, Protocol Buffers
Stream processor and streaming SQL
Apache Flink, Apache Spark Structured Streaming
Open table format
Apache Iceberg, Delta Lake
Local multi-service environment
Docker Compose, Podman

How the work is assessed

  • Supervised AI-off check: predict window outputs and failure effects from event timelines (20%)
  • Graded labs (30%)
  • Capstone repository on a five-criterion rubric with defence (50%)
To pass
70% overall and at least 60% on both the check and the capstone

Use of AI in the course

AI-off for the supervised check and the windows lab. AI-tutor in the other labs. AI-full in the capstone, defended live.

AI-off: no AI assistance. AI-tutor: an assistant that hints and explains but does not give the answer. AI-full: any assistance; the participant owns the result and defends it.
