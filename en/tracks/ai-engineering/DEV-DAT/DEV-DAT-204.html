DEV-DAT-204 Data Quality, Contracts and Observability

  • Level 200 · Apply
  • Intensive
  • 24 h
  • Audience: practitioner

Track

AI Engineering

Stream

DEV-DAT Data Engineering and Architecture

Level

Level 200 · Apply

Audience

practitioner

Format

Intensive: 3 teaching days and a capstone day, with guided pre-work and a tracked follow-up task

Total hours

24 h

Prerequisites

  • DEV-DAT-201 Modern Data Engineering
  • Runs and edits an orchestrated pipeline locally

Description

Participants put quality controls into the synthetic claims platform of a fictional health insurer. They profile the sources, turn consumer requirements into executable rules, extend the contract basics of DEV-DAT-201 with versioning and service levels, and gate every build on them. Pipelines emit lineage and run events, which participants use to find the blast radius of a seeded incident, quarantine bad data, notify consumers and write a post-incident review. The quality programme and stewardship side is LDS-DMG-203.

Learning outcomes

By the end, the participant can:

  1. Awareness

    Describe the data quality dimensions and match each to a check that runs inside a pipeline.

    Given eight described defects.

    Evidence a mapping matching the reference on six of eight.

  2. Applied

    Analyse tables with column, relationship and dependency profiling to propose rules.

    Given four claims tables with seeded defects.

    Evidence a report listing each rule, its threshold and the defect it catches.

  3. Applied

    Implement rules with thresholds, severities and quarantine actions as pipeline gates.

    Given an orchestrated pipeline.

    Evidence a run in which one rule warns, one blocks publication and bad rows land in quarantine.

  4. Applied

    Implement contract versioning with breaking-change rules and service-level clauses for freshness and ownership, checked in continuous integration.

    Given an open-standard contract and two planned producer schema changes.

    Evidence runs that reject the breaking change, accept the compatible one and bump the version.

  5. Applied

    Configure lineage and run events across the pipeline and use them to list affected downstream assets.

    Given a seeded upstream defect.

    Evidence an impact list matching the reference set.

  6. Performance

    Diagnose a data incident from alerts, lineage and logs, and lead it to closure.

    Given a timed simulated incident and a consumer pressing for answers.

    Evidence a timeline, consumer notice and blameless review.

Topics

Dimensions, profiling and rules

  • Accuracy, completeness, consistency, timeliness, validity, uniqueness
  • Column, relationship and dependency profiling
  • Critical data elements first
  • Rules with scope, threshold, severity and owner
  • Quality scores and trend reports

Gates in pipelines

  • Warn, block or quarantine
  • Write, audit, publish
  • Volume and distribution anomalies

Data contracts

  • Producer and consumer duties
  • Service-level clauses: freshness, completeness, support
  • Versioning and breaking-change rules in continuous integration

Lineage and observability

  • Lineage as events emitted by runs
  • Freshness, volume and schema signals
  • Alert routing and fatigue

Incident handling

  • Triage and consumer notice
  • Root cause through lineage
  • Backfills, corrections and blameless reviews

Tools and platforms

These are examples. Any equivalent tool may be used instead.

Validation framework
Great Expectations, Soda Core, Pandera
Data contract specification
Open Data Contract Standard (ODCS), contract checks compiled to SQL tests
Lineage events
OpenLineage with Marquez, the orchestrator's built-in lineage
Orchestrator and engine
Dagster with DuckDB, Apache Airflow with PostgreSQL
Metrics and alerting
Prometheus with Grafana, the orchestrator's alerting
Continuous integration
GitHub Actions, GitLab CI

How the work is assessed

  • Supervised AI-off check: write rules and thresholds for described defects (20%)
  • Graded labs (30%)
  • Follow-up repository and live incident diagnosis on a five-criterion rubric (50%)
To pass
70% overall and at least 60% on both the check and the follow-up review

Use of AI in the course

AI-off for the supervised check and the profiling lab. AI-tutor in the other labs, including the incident drill. AI-full in the follow-up task, defended live.

AI-off: no AI assistance. AI-tutor: an assistant that hints and explains but does not give the answer. AI-full: any assistance; the participant owns the result and defends it.
