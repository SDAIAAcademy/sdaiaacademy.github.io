DEV-DAT-301 Data Modelling: Conceptual to Semantic

  • Level 300 · Develop
  • Intensive
  • 30 h
  • Audience: practitioner

Track

AI Engineering

Stream

DEV-DAT Data Engineering and Architecture

Level

Level 300 · Develop

Audience

practitioner

Format

Intensive: 4 teaching days and a capstone day, with guided pre-work and a tracked follow-up task

Total hours

30 h

Prerequisites

  • FND-DAT-101 SQL and Relational Data
  • DEV-DAT-201 Modern Data Engineering
  • Reads and writes table definitions with keys and constraints

Description

Participants model one domain of a fictional water utility, from interviews and undocumented source schemas to a semantic model. They derive conceptual and normalised logical models, then implement a dimensional mart, an auditable vault layer and a wide feature table, measuring each under its intended queries. They publish a semantic model over the mart and review language-model-generated schemas against modelling standards. Every choice is recorded and defended. Metrics as code and dashboards are DEV-DAT-202; ontologies and knowledge graphs continue in DEV-DAT-304.

Learning outcomes

By the end, the participant can:

  1. Awareness

    Compare normalised, dimensional, vault and wide-table models by the change, history and query patterns each serves.

    Given five described workloads.

    Evidence a choice table matching the reference on four of five.

  2. Applied

    Prepare conceptual and normalised logical models from interviews and source-system analysis.

    Given transcripts and three undocumented synthetic databases.

    Evidence a versioned diagram-as-code model with keys, definitions and rules, checked against a hidden reference.

  3. Performance

    Design a dimensional model with declared grain, conformed dimensions and chosen history types, and implement it.

    Given six analytical questions.

    Evidence table definitions and load code answering all six, with a decision record.

  4. Performance

    Design a vault layer and a wide feature table and optimise their physical layout.

    Given an audit requirement, a training use case and a query benchmark.

    Evidence benchmark results before and after layout changes, with trade-offs explained.

  5. Applied

    Implement a semantic model of entities, measures and dimensions carrying definitions and classification tags.

    Given the mart and a metric glossary.

    Evidence semantic queries returning the reference figures.

  6. Performance

    Review a generated schema against modelling standards and defend the corrections.

    Given seeded flaws in keys, grain, naming and history.

    Evidence a structured review with every flaw, its consequence and a fix, defended live.

Topics

Conceptual and logical modelling

  • Entities and business rules from interviews
  • Normal forms and when to stop
  • Natural, surrogate and composite keys
  • Diagram-as-code notation

Source analysis

  • Schema inspection and reverse engineering
  • Profiling for keys and dependencies
  • Conflicting definitions across systems

Dimensional design

  • Grain, facts and conformed dimensions
  • Slowly changing dimension types and bitemporal history
  • Degenerate, role-playing and bridge structures

Vault, wide tables and physical design

  • Hubs, links and satellites
  • Wide tables for lakehouse engines
  • Partitioning, clustering and indexing
  • Reference data and code sets

Semantic models and review

  • Measures and dimensions for reporting tools and agents
  • Standards, naming and model repositories
  • Schema evolution and backward-compatible change
  • Reviewing generated schemas

Tools and platforms

These are examples. Any equivalent tool may be used instead.

Diagram-as-code modelling
DBML, Mermaid entity-relationship diagrams, PlantUML
Relational and analytical databases
PostgreSQL, DuckDB
Transformation framework
SQLMesh, dbt
Semantic layer
Cube Core, the transformation framework's semantic layer
Language model for schema generation
a locally served open-weight model, any organisation-approved assistant

How the work is assessed

  • Supervised AI-off check: normalise a schema and declare grain (20%)
  • Graded labs (30%)
  • Capstone package and panel defence on a five-criterion rubric (50%)
To pass
70% overall and at least 60% on both the check and the capstone

Use of AI in the course

AI-off for the supervised check and the source-analysis lab. AI-tutor in the other labs; in the review lab the generated schema is the object under review. AI-full in the capstone, defended live.

AI-off: no AI assistance. AI-tutor: an assistant that hints and explains but does not give the answer. AI-full: any assistance; the participant owns the result and defends it.
