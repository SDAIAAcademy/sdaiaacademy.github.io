DEV-SWE-301 System Design for AI Products

  • Level 300 · Develop
  • Intensive
  • 30 h
  • Audience: practitioner

Track

AI Engineering

Stream

DEV-SWE Software Engineering for AI Builders

Level

Level 300 · Develop

Audience

practitioner

Format

Intensive: 4 teaching days and a design-review day, with guided pre-work and a tracked follow-up task

Total hours

30 h

Prerequisites

  • DEV-SWE-202 Back-End Services and Interfaces for AI Applications
  • DEV-LLM-201 Building Applications on Language Models
  • Has maintained a service with a database and an external API dependency

Description

Participants design AI products as systems rather than prompts. On a synthetic bilingual permit assistant that retrieves regulations, parses uploads, drafts decisions and files them after human approval, they decide what is plain code, workflow, model call or agent, place every piece of state, set latency and cost budgets per user task, and plan degradation when a model is slow, wrong or down. A walking skeleton with fault injection tests the design, and a panel review closes the course.

Learning outcomes

By the end, the participant can:

  1. Awareness

    Explain how non-determinism, token-priced compute, provider limits and model changes alter service design.

    Given three incident write-ups.

    Evidence an analysis linking each incident to the design property it violated.

  2. Applied

    Prepare a latency and cost budget per user task, including time to first token and cost per successful task.

    Given recorded traces and a price sheet.

    Evidence a budget that agrees with measured runs within a stated tolerance.

  3. Applied

    Analyse the failure modes of a design and attach a detection signal and degradation response to each.

    Given the case-study design.

    Evidence a failure-mode table that includes wrong but confident outputs.

  4. Performance

    Design the decomposition and state placement of an AI product.

    Given an unseen brief with quality, latency and data-classification constraints.

    Evidence a design document with decision records naming rejected alternatives.

  5. Performance

    Build a walking skeleton whose degradation paths hold the budget under injected faults.

    Given a mock provider with scripted delays, errors and malformed output.

    Evidence fault-injection logs showing fallback, queueing and human hand-off.

  6. Performance

    Review a peer design and defend one's own when the panel changes a constraint.

    Given a panel review.

    Evidence a written review and the revised decision.

Topics

What AI components change

  • Non-determinism, token pricing and provider limits
  • Models that change or retire; keeping a provider exit
  • Code first, workflows before agents

Decomposition and state

  • Boundaries between code, workflow, model call and agent
  • Monolith or services, decided by experiment
  • Where conversation, memory, documents and job state live
  • Idempotent steps and event logs
  • Caches and cache-aware prompt layout

Budgets

  • Quality targets and where evaluation runs
  • Latency at the 95th percentile
  • Cost per successful task
  • Rate limits and model tiers

Failure and degradation

  • Failure-mode analysis
  • Timeouts, circuit breakers and bulkheads
  • Fallback models, cached answers and human hand-off
  • Limiting the blast radius of actions

Design reviews

  • Decision records and trade-off tables
  • Security, privacy and data-placement checklists
  • Hand-offs to DEV-INF-404 and DEV-OPS-304

Tools and platforms

These are examples. Any equivalent tool may be used instead.

Diagrams and decision records
C4 model with Structurizr, Mermaid, Markdown decision records
Fault injection
Toxiproxy, a scripted mock provider
Tracing
OpenTelemetry with Jaeger, Langfuse, Arize Phoenix
Load testing
k6, Locust
Language model access
a locally served open-weight model, any commercial API

How the work is assessed

  • AI-off check: compute a budget from given figures (15%)
  • Graded labs (30%)
  • Capstone on a five-criterion rubric (35%)
  • Panel defence and peer review (20%)
To pass
60% overall and at least 60% on the capstone

Use of AI in the course

AI-off for the budget check. AI-tutor while drafting decompositions. AI-full for the skeleton and capstone, defended before a panel.

AI-off: no AI assistance. AI-tutor: an assistant that hints and explains but does not give the answer. AI-full: any assistance; the participant owns the result and defends it.
