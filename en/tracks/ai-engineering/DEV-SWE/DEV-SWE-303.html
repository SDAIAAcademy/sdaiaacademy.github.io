DEV-SWE-303 Shaping the Build: Product Sense and Forward-Deployed Practice

  • Level 300 · Develop
  • Workshop
  • 16 h
  • Audience: practitioner

Track

AI Engineering

Stream

DEV-SWE Software Engineering for AI Builders

Level

Level 300 · Develop

Audience

practitioner

Format

Workshop: two days of role-played engagement and a short build, with guided pre-work

Total hours

16 h

Prerequisites

  • DEV-SWE-201 Software Engineering with Coding Agents
  • Has shipped a language model application

Description

Participants practise the engineer's side of forward-deployed work: deciding what to build with the people who will use it. In a role-played engagement with a fictional municipal licensing office, they interview staff, write the specification, test the riskiest assumption with a time-boxed prototype, cost the value case, and hand over a system the client can run alone. Product managers take LDS-PRD-201; full business cases are LDS-ADV-201.

Learning outcomes

By the end, the participant can:

  1. Applied

    Analyse a workflow from interviews to find where AI would change an outcome users care about.

    Given role-played interviews and a synthetic process log.

    Evidence a workflow map with pain points ranked by frequency and cost.

  2. Performance

    Design a specification with success metrics, non-goals, acceptance criteria written as evaluation cases, data needs and risks.

    Given the discovery findings.

    Evidence a specification accepted by the stakeholder role-player.

  3. Applied

    Test the riskiest assumption with a time-boxed prototype and short user sessions.

    Given a coding agent and synthetic data.

    Evidence session notes that confirm or refute the assumption.

  4. Performance

    Decide whether to stop, iterate or build, backed by a value case with sensitivity.

    Given prototype results and price assumptions.

    Evidence a decision log and value sheet naming the assumptions that would reverse it.

  5. Performance

    Deliver a hand-over package the client team can run and change alone.

    Given the prototype and specification.

    Evidence a runbook, evaluation set and ownership table reviewed by the receiving team.

Topics

Discovery

  • Interviews about past behaviour
  • Workflows and their exceptions
  • Saying no to a use case

Specification as the deliverable

  • Problem, users and non-goals
  • Acceptance criteria as evaluation cases
  • Data, permission and classification needs

Minimum viable decisions

  • Riskiest assumption first
  • Reversible and irreversible choices
  • Cost per successful task and break-even

Hand-over

  • Runbooks and evaluation sets
  • Ownership and exit criteria
  • Training the receiving team

Tools and platforms

These are examples. Any equivalent tool may be used instead.

Coding agent and model access
OpenCode, goose, an open-weight model, any commercial API
Workflow mapping
Excalidraw, bpmn.io
Value modelling
a spreadsheet, a Python notebook

How the work is assessed

  • AI-off task: rewrite a vague request as testable criteria (15%)
  • Specification (20%)
  • Other labs (15%)
  • Hand-over package (25%)
  • Presentation and panel questions (25%)
To pass
60% overall and at least 60% on the specification

Use of AI in the course

AI-off for the supervised task and interviews. AI-tutor for the specification. AI-full for the defended prototype and value case.

AI-off: no AI assistance. AI-tutor: an assistant that hints and explains but does not give the answer. AI-full: any assistance; the participant owns the result and defends it.
