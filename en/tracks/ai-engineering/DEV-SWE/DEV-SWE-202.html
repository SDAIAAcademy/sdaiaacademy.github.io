DEV-SWE-202 Back-End Services and Interfaces for AI Applications

  • Level 200 · Apply
  • Intensive
  • 30 h
  • Audience: practitioner

Track

AI Engineering

Stream

DEV-SWE Software Engineering for AI Builders

Level

Level 200 · Apply

Audience

practitioner

Format

Intensive: 4 teaching days and a capstone day, with guided pre-work and a tracked follow-up task

Total hours

30 h

Prerequisites

  • FND-PRG-105 Computer Systems and Cloud Essentials for AI Work
  • Has called a language model API from Python
  • Writes unit tests in Python
  • Writes SQL against a relational database

Description

Participants build the service between users and language models. On a synthetic citizen-enquiry assistant they define a typed API contract, stream model output, move batch summarisation onto a queue with retries and idempotency, add sign-in, per-user authorisation and quotas, and persist conversations and job state so the service survives restarts. A deterministic fake model with scripted latency keeps labs and the load test on a laptop; a small open-weight model serves end-to-end checks. Deployment continues in DEV-OPS-201.

Learning outcomes

By the end, the participant can:

  1. Awareness

    Distinguish request-response, streaming and asynchronous job patterns and state which fits a given model call.

    Given six described features.

    Evidence a decision table matching the reference on five rows.

  2. Applied

    Implement a typed API contract that validates model output and maps provider failures to stable error codes.

    Given a fake model returning malformed output and errors.

    Evidence a machine-readable API specification and passing contract tests.

  3. Applied

    Implement token streaming with cancellation and clean handling of client disconnects.

    Given a client that drops mid-stream.

    Evidence a test showing the upstream call stops, and logged time to first token.

  4. Applied

    Implement queued jobs with idempotency keys, retries with backoff and a status endpoint.

    Given duplicate submissions and injected provider failures.

    Evidence a run log in which each job takes effect once and failures reach a dead-letter queue.

  5. Applied

    Configure sign-in, per-user authorisation and quotas.

    Given a local identity provider and two test users.

    Evidence tests in which cross-user access fails and a quota stops model calls.

  6. Performance

    Build a service that persists state, recovers from a restart and meets a latency budget under load.

    Given an unseen feature brief and a concurrency target.

    Evidence a repository with tests and a load-test report, defended live.

Topics

Contracts

  • Resource design and versioning
  • Validating model output at the boundary
  • Error mapping for timeouts, refusals and outages
  • Provider-neutral clients and gateways

Streaming

  • Server-sent events and WebSockets
  • Time to first token
  • Cancellation and disconnects
  • Streaming tool-call events

Asynchronous work

  • Queues and workers
  • Idempotency and at-least-once delivery
  • Backoff, jitter and dead-letter queues
  • Status endpoints and webhooks

Identity, limits and state

  • OpenID Connect and token validation
  • Provider keys held server-side only
  • Tenant isolation, quotas and spend caps
  • Conversations and tool calls as stored data
  • Retention and deletion

Readiness

  • Fake models for tests
  • Load tests against a budget
  • Structured logs and trace identifiers

Tools and platforms

These are examples. Any equivalent tool may be used instead.

Web framework
FastAPI, Flask, Node.js with Express
Provider-neutral model access
a locally served open-weight model, LiteLLM in front of any provider
Queue and workers
Redis with RQ, RabbitMQ with Celery
Relational database
PostgreSQL, SQLite
OpenID Connect identity provider
Keycloak, Dex
Schema validation
Pydantic, Zod
Load testing
k6, Locust

How the work is assessed

  • AI-off check: predict a handler's behaviour under failure (15%)
  • Graded labs (35%)
  • Capstone on a five-criterion rubric (30%)
  • Live defence (20%)
To pass
60% overall and at least 60% on the capstone

Use of AI in the course

AI-off for the supervised check and the first implementation of idempotent jobs. AI-tutor in other labs. AI-full in the capstone, which is defended live.

AI-off: no AI assistance. AI-tutor: an assistant that hints and explains but does not give the answer. AI-full: any assistance; the participant owns the result and defends it.
