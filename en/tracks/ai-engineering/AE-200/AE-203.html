AE-203 Building Applications on Language Models

  • Level 200 · Apply
  • Intensive
  • 26 h
  • Audience: practitioner

Track

AI Engineering

Stream

AE-200 AI Engineering: courses that help prepare for the Assistant level

Level

Level 200 · Apply

Audience

practitioner

Format

Intensive: 4 teaching days of four sessions and a capstone day, with guided pre-work and a tracked follow-up task

Total hours

26 h

Prerequisites

  • FN-101 Python for Data and AI Work
  • FN-102 Command Line, Git and Reproducible Projects
  • FN-105 How Machine Learning and Language Models Work
  • Calls a web API from Python and handles JSON
  • Writes and runs unit tests

Badge

Helps prepare for the SDAIA AI Engineering badge, Assistant level.

Description

Participants build a bilingual rider assistant for a fictional transit authority on top of any language model, hosted or open-weight. They call models through a provider-neutral interface, extract validated structured data from rider messages, add tool calls to a synthetic trip-status service, ground answers in a policy corpus with citations and abstention, write a small evaluation set and run the assistant against it, and add input and output checks for personal data and instruction-like text. The result is a small tested web service.

Learning outcomes

By the end, the participant can:

  1. Awareness

    Compare the main model API shapes and identify what changes in code when an application switches provider or moves to a local model.

    Given the same request written for three interfaces.

    Evidence an annotated comparison table that matches the reference on message structure, tool calls and usage reporting.

  2. Applied

    Implement structured extraction from free-text messages with schema validation, bounded retries and a fallback path.

    Given 300 synthetic Arabic and English rider messages and a target schema.

    Evidence an extraction module with tests and a measured valid-output rate against a stated target.

  3. Applied

    Implement tool calling for two services with typed arguments, argument validation and handling of tool errors.

    Given a synthetic trip-status service and a ticket-creation service.

    Evidence a passing test suite that includes malformed calls, timeouts and tool errors.

  4. Applied

    Implement a grounded answering step that retrieves policy passages, cites them and declines when the corpus holds no answer.

    Given 120 bilingual policy pages and 30 questions the corpus cannot answer.

    Evidence answers whose citations are checked automatically and a measured abstention rate.

  5. Applied

    Prepare a small evaluation set and measure the assistant with code-based checks and one model-graded check validated against labels.

    Given 40 labelled cases across extraction, tool use and grounded answers.

    Evidence an evaluation run with pass rates per category and the grader's agreement with the labels.

  6. Applied

    Configure input and output checks for personal data, off-topic requests and instruction-like text inside retrieved content.

    Given 30 seeded risky messages and documents.

    Evidence a before-and-after table of blocked, masked and passed cases with false positives counted.

  7. Performance

    Build a bilingual assistant service that combines structured extraction, tool calls and grounded answers behind a tested API.

    Given the case corpus and services, a provider-neutral client and a cost limit per 1,000 requests.

    Evidence a locally runnable service whose repository README reports evaluation results and cost from two measured runs.

Topics

Calling models

  • Tokens, context and cost
  • Chat, response and message API shapes, and the Open Responses specification
  • Provider-neutral clients and gateways
  • Prompt caching and stable context order
  • Streaming, timeouts and retries
  • Choosing a model per task

Prompts as code

  • System and user instructions
  • Examples in the prompt
  • Templates under version control
  • A prompt change is a release

Structured outputs

  • JSON Schema
  • Constrained decoding versus validate and retry
  • Typed models in code
  • Fallback to a human queue

Tool calling

  • Tool schemas
  • The call, execute and return cycle
  • Argument validation and tool errors
  • Workflow or agent
  • Tool servers over the Model Context Protocol (MCP), at concept level

Grounded answers

  • Chunking and indexing
  • Lexical, dense and hybrid search
  • Citations
  • Abstention
  • Arabic text normalisation

Small evaluations

  • Golden cases
  • Code-based checks
  • One model grader checked against labels
  • Re-running on every change

Input and output safety

  • Personal data detection and masking
  • Instruction-like text in retrieved content
  • Output validation
  • Logging without leaking

Shipping the service

  • A web API around the assistant
  • Tests with recorded model responses
  • Configuration and secrets

Day by day

Four sessions a day. Each session presents the concepts with a demonstration, then ends in a lab.

#SessionLab
Day 1 Calling models well
1.1Tokens, context and costCount tokens for Arabic and English rider messages and estimate daily cost and latency for 10,000 messages
1.2Three API shapes, one interfaceSend the same request to a hosted and a local model through one client and compare the responses and usage fields
1.3Prompts as versioned codeMove the assistant's instructions into a versioned template and write two tests that pin its behaviour
1.4Streaming, timeouts and retriesAdd a timeout, a retry with backoff and a fallback model, and test them against a simulated slow endpoint
Day 2 Structured data and tools
2.1Schemas for model outputExtract route, date and complaint type from 50 messages into a typed schema and measure the valid rate
2.2Validation, retry and fallbackFeed validation errors back to the model, cap the retries and route failures to a human queue
2.3Tool callingExpose the trip-status service as a tool and handle a correct call, a malformed call and a tool error
2.4Workflow or agentWrite one task as a fixed workflow and as a tool loop and compare steps, cost and failures on ten cases
Day 3 Grounded answers
3.1Chunking and indexing a policy corpusChunk the Arabic and English policy pages two ways and index both versions
3.2Lexical, dense and hybrid searchCompare keyword, embedding and combined search on 30 questions with known source pages
3.3Answers with citationsGenerate answers that cite page and section and check automatically that each citation exists
3.4Saying the answer is not thereAdd an abstention rule and measure it on 30 questions the corpus cannot answer
Day 4 Evaluate, protect and ship
4.1A small evaluation setWrite 40 golden cases with code-based checks and run them against the assistant
4.2One model grader, checked against labelsWrite a binary faithfulness grader and measure its agreement with 30 labelled answers
4.3Input and output checksMask personal data in messages and logs and flag instruction-like text found in retrieved pages
4.4Packaging the assistant as a serviceWrap the assistant in a web API with a health check and run the tests against recorded model responses

Tools and platforms

These are examples. Any equivalent tool may be used instead.

Language model access
a free hosted open-weight model, a locally served open-weight model, any commercial API
Provider-neutral client or gateway
LiteLLM, an OpenAI-compatible local server such as llama.cpp server or Ollama
Schema validation and structured output
Pydantic, Instructor, Outlines
Embeddings and vector search
Sentence Transformers with FAISS, pgvector, Chroma
Lexical search
SQLite full-text search, rank-bm25
Personal data detection
Presidio, regular-expression and dictionary rules
Web service framework
FastAPI, Flask
Evaluation harness
pytest with custom assertions, promptfoo, Inspect

How the work is assessed

  • Supervised entry quiz and exit check without AI assistance: read a request and response trace, spot a schema violation, estimate token cost, find instruction-like text in a retrieved passage (20%)
  • Capstone repository scored on a five-criterion rubric: working service and tests 25, structured output and tools 20, grounding and abstention 20, evaluation 20, safety checks and limits 15 (60%)
  • Live defence in which the participant runs the evaluation and explains a failing case the assessor selects (20%)
To pass
70% overall, with at least 60% on the capstone rubric and at least 60% on the supervised check

Use of AI in the course

AI-off for the supervised checks and for the first attempt at the schema and tool-calling labs. AI-tutor in the other labs: the course assistant hints and explains but does not write the module. AI-full in the capstone, which the participant defends live.

AI-off: no AI assistance. AI-tutor: an assistant that hints and explains but does not give the answer. AI-full: any assistance; the participant owns the result and defends it.
