AE-205 Deploying AI Services: Containers, Serving and Monitoring

  • Level 200 · Apply
  • Intensive
  • 26 h
  • Audience: practitioner

Track

AI Engineering

Stream

AE-200 AI Engineering: courses that help prepare for the Assistant level

Level

Level 200 · Apply

Audience

practitioner

Format

Intensive: 4 teaching days of four sessions and a capstone day, with guided pre-work and a tracked follow-up task

Total hours

26 h

Prerequisites

  • FN-102 Command Line, Git and Reproducible Projects
  • AE-201 Machine Learning Foundations and Model Evaluation
  • Runs commands in a Linux shell
  • Has trained a model and saved it to a file

Badge

Helps prepare for the SDAIA AI Engineering badge, Assistant level.

Description

Participants take two trained models from a notebook to a monitored service. For a fictional mutual insurer they package a claims-triage classifier and a similar-claims embedding model with pinned dependencies, register model versions, serve them behind a versioned API with input validation, build and scan a container image, run it on a single-node local cluster with health checks, add metrics, structured logs and traces, load-test and size the service, release a new version by canary and roll it back, and detect drift in a replayed stream of claims.

Learning outcomes

By the end, the participant can:

  1. Awareness

    Explain the path from a trained model to a served prediction, naming the artefact, image, registry, runtime, endpoint and monitor at each step.

    Given a deployment diagram with the components unlabelled.

    Evidence a labelled diagram with a one-sentence role for each component, scored against the reference.

  2. Applied

    Prepare a model artefact with pinned dependencies, a version, an input and output signature and a reproducible build.

    Given a trained model and its training script.

    Evidence a registered model version that a fresh environment loads and that reproduces ten reference predictions.

  3. Applied

    Implement a versioned prediction API with input validation, typed errors and separate health and readiness checks.

    Given the registered model and an API contract.

    Evidence a passing contract test suite, including malformed inputs and a model file that fails to load.

  4. Applied

    Configure a container image for the service, scan it for vulnerabilities and run it with resource limits on a single-node cluster.

    Given the service code and a base image.

    Evidence an image under a stated size, a scan report with no critical findings and a deployment that passes its readiness check.

  5. Applied

    Implement metrics, structured logs and traces for the service and a dashboard for latency percentiles, error rate and prediction distribution.

    Given the running service and a load generator.

    Evidence a dashboard defined as code and an alert rule that fires on a seeded error spike.

  6. Applied

    Measure latency and throughput under load and size workers and replicas to meet a latency objective at the lowest cost.

    Given a target request rate and a 95th-percentile latency objective set by the insurer, on laptop CPUs.

    Evidence a load-test report with the chosen configuration and its cost per 1,000 predictions.

  7. Performance

    Deliver a new model version by canary release, decide on promotion or rollback from monitored metrics and detect drift in replayed traffic.

    Given two model versions, four weeks of replayed claims with injected drift and written rollback criteria.

    Evidence a release log with the decision and its evidence, a completed rollback and a drift report naming the shifted features.

Day by day

Four sessions a day. Each session presents the concepts with a demonstration, then ends in a lab.

#SessionLab
Day 1 Package and serve
1.1From notebook to artefactExport the claims-triage model with its signature and pinned dependencies and reload it in a clean environment
1.2A registry for model versionsRegister two supplied model versions with metrics and tags and load one by version
1.3A prediction API with a contractBuild a versioned prediction endpoint that validates inputs and returns typed errors
1.4Health, readiness and warm-upAdd health and readiness checks and show how they differ when the model file is missing
Day 2 Containers and a cluster
2.1Images that are small and reproducibleWrite a multi-stage container file and compare its size and build time with a naive one
2.2Scanning and configurationScan a supplied image, fix one critical finding and move secrets out of the image into configuration
2.3Running on a local clusterDeploy the supplied service image to a single-node cluster with probes and resource limits
2.4Serving the embedding modelAdd the similar-claims endpoint and compare its memory use and start-up time with the classifier
Day 3 Observe and size
3.1Metrics that matterExpose request rate, error rate and latency histograms and graph the 50th, 95th and 99th percentiles
3.2Logs and tracesAdd structured logs with a request id, redact personal fields and follow one slow request through a trace
3.3Load testingRun a load test at three request rates and find where latency breaks the objective
3.4Sizing and costTune workers and replicas to meet the latency objective and compute cost per 1,000 predictions
Day 4 Release and watch
4.1Rolling, canary and shadow releasesSend 10% of traffic to a new version and compare its metrics with the current one
4.2Rollback on evidenceTrigger the rollback criteria with a seeded faulty version and roll back within five minutes
4.3Drift in replayed trafficReplay four weeks of claims, compute a drift statistic per feature and name the shifted ones
4.4Alerts and a runbookWrite two alert rules and a one-page runbook for the on-call engineer, then choose the capstone model

How the work is assessed

  • Supervised entry quiz and exit check without AI assistance: read a container file and a manifest, interpret a latency histogram, choose a release strategy for a scenario (20%)
  • Capstone repository scored on a five-criterion rubric: packaging and API 20, container and deployment 20, observability 20, sizing against the objective 15, release, rollback and drift 25 (60%)
  • Live defence in which the participant rolls back a version and explains a dashboard the assessor selects (20%)
To pass
70% overall, with at least 60% on the capstone rubric and at least 60% on the supervised check

Use of AI in the course

AI-off for the supervised checks and for the first attempt at the container file and the alert rules. AI-tutor in the other labs: the course assistant explains errors and suggests the next step without writing the manifest. AI-full in the capstone, which the participant defends live.

AI-off: no AI assistance. AI-tutor: an assistant that hints and explains but does not give the answer. AI-full: any assistance; the participant owns the result and defends it.
