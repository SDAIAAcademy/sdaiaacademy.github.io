AE-390 AI Engineering Practicum

  • Level 300 · Develop
  • Practicum
  • 100 h
  • Audience: practitioner

Track

AI Engineering

Stream

AE-300 AI Engineering: courses that help prepare for the Associate level

Level

Level 300 · Develop

Audience

practitioner

Format

Practicum: about eight weeks part-time in teams of three to five for a sponsoring organisation, with weekly reviews by experienced engineers, two gate reviews and a defence before the sponsor

Total hours

100 h

Prerequisites

  • AE-302 Agentic Systems Engineering: Loops, Context and Harnesses
  • AE-303 Evaluation-Driven Development for Language Model Applications
  • AE-304 Retrieval and Knowledge Engineering for Language Model Systems
  • AE-305 Operating Machine Learning and Language Model Systems
  • AE-308 Securing Language Model and Agent Applications
  • AE-311 Shaping the Build: Product Sense and Delivery Practice
  • Works in a team through branches, pull requests and code review
  • Can give about twelve hours a week for eight weeks

Badge

Helps prepare for the SDAIA AI Engineering badge, Associate level.

Description

Teams of three to five take one problem from a sponsoring government entity or company from scoping to a shipped AI system in about eight weeks part-time. They agree a specification and acceptance criteria with the sponsor, build in weekly iterations reviewed by experienced engineers, evaluate against the criteria with a regression gate, harden the system after another team attacks it, deploy it with service objectives, monitoring and a rehearsed rollback, and hand it over with an evaluation report, a security note and an operations plan. Sponsor data enters only as an anonymised extract or a synthetic replica built to the sponsor's schema.

Learning outcomes

By the end, the participant can:

  1. Applied

    Analyse a sponsor's problem through discovery and translate it into a specification with acceptance criteria and a data-handling plan.

    Given sponsor interviews, process walk-throughs and the sponsor's data rules.

    Evidence a specification and data-handling plan approved at gate one.

  2. Performance

    Build, as a team, a working AI system that meets the agreed acceptance criteria, with coding-agent output reviewed in proportion to risk.

    Given weekly iterations and reviews by experienced engineers.

    Evidence a repository with commit history, review threads and passing continuous integration.

  3. Performance

    Evaluate the system against the sponsor's criteria with error analysis and a regression gate.

    Given an evaluation set the team owns and the sponsor accepts.

    Evidence an evaluation report with measured results, slices by language and user group, and a gate that blocks a seeded regression.

  4. Performance

    Harden the system after a cross-team attack and record the residual risks the sponsor must accept.

    Given a threat model and a cross-team adversarial testing day.

    Evidence a security note with findings, fixes and regression tests.

  5. Performance

    Deploy the system with service objectives, capacity sizing, monitoring, cost per successful task and a rehearsed rollback.

    Given the sponsor's hosting constraints and expected load.

    Evidence an operations plan and the log of a rollback and incident drill.

  6. Performance

    Defend the system, the team's design decisions and one's own contribution before the sponsor and experienced engineers.

    Given a demonstration and individual questions on code the panel selects.

    Evidence the panel's scored defence record.

Topics

Engagement and scoping

  • Sponsor roles, agreements and intellectual property
  • Discovery and the problem brief
  • Acceptance criteria as the contract
  • Change control during delivery

Team delivery

  • Weekly iterations and demonstrations
  • Coding agents with review by risk
  • Tests, continuous integration and decision records

Data and governance

  • Classification of sponsor data
  • Anonymised extracts and synthetic replicas
  • Data sent to external models
  • Impact assessment and system card

Quality and security

  • Owning the evaluation set
  • Error analysis and regression gates
  • Threat model and cross-team attack day

Operations and hand-over

  • Service objectives, capacity and monitoring
  • Cost per successful task
  • Runbooks, rollback drills and ownership after the practicum

Tools and platforms

These are examples. Any equivalent tool may be used instead.

Version control, review and continuous integration
Git with Forgejo, Git with GitLab, Git with GitHub
Coding agent
OpenCode, goose, any commercial coding agent the sponsor's data rules allow
Language model access
a locally served open-weight model, any commercial API the data-handling plan allows
Evaluation harness
Inspect, promptfoo, pytest with custom assertions
Tracing and monitoring
OpenTelemetry with Langfuse, Prometheus with Grafana
Containers and deployment
Podman or Docker, k3s
Security scanning and personal-data detection
Semgrep, OSV-Scanner, Presidio

How the work is assessed

  • Gate one and gate two reviews by experienced engineers (20%)
  • Team deliverables on a six-criterion rubric: working system against acceptance criteria 25, evaluation report 20, security note 15, operations plan and drill 15, architecture and cost 15, hand-over 10 (50%)
  • Individual defence, including code reading without AI assistance on a module the panel selects (30%)
To pass
Both gates passed, 70% overall and at least 60% in the individual defence

Use of AI in the course

AI-full for building, with coding-agent transcripts kept in the repository and review in proportion to risk; sponsor data goes only to models the data-handling plan allows. AI-off for the individual code-reading part of the defence.

AI-off: no AI assistance. AI-tutor: an assistant that hints and explains but does not give the answer. AI-full: any assistance; the participant owns the result and defends it.
