AE-303 Evaluation-Driven Development for Language Model Applications

  • Intensive
  • 26 h
  • Audience: practitioner

AI Engineering

Stream

Level

Level 300 · Develop

practitioner

Format

Intensive: 4 teaching days of four sessions and a capstone day, with guided pre-work and a tracked follow-up task

Total hours

26 h

Prerequisites

  • AE-203 Building Applications on Language Models
  • Reads a confusion matrix and computes precision and recall
  • Has run a test suite in continuous integration

Badge

Helps prepare for the SDAIA AI Engineering badge, Associate level.

Description

Participants treat evaluation as the specification of a language model application. Working on one synthetic case, a bilingual service assistant for a fictional licensing office, they read traces, name the failure modes, turn them into code-based checks and calibrated model-graded checks, evaluate an agent over repeated trials, compare two configurations with a sound statistical test, and wire the suite into a regression gate. Every number a participant reports comes from a run they executed.

Learning outcomes

By the end, the participant can:

  1. Awareness

    Distinguish code-based checks, model-graded checks and human review, and state when each is the cheapest reliable instrument.

    Given six described failure modes of the case assistant.

    Evidence a decision table that matches the reference on at least five of six rows.

  2. Applied

    Carry out open and axial coding of traces to produce a failure taxonomy with counts.

    Given 100 Arabic and English traces from the case assistant.

    Evidence a taxonomy file with at least five failure modes, each with a definition, three trace ids and a frequency.

  3. Applied

    Implement code-based evaluators for structure, grounding and policy rules.

    Given the taxonomy and a provided harness.

    Evidence a suite that runs unattended and reports pass rates per failure mode.

  4. Applied

    Calibrate a model-graded evaluator against human labels and report its agreement with an interval.

    Given 60 labelled examples split into development and held-out sets.

    Evidence a calibration report with true-positive and true-negative rates on the held-out set.

  5. Performance

    Evaluate an agent on multi-step tasks for outcome and consistency over repeated trials.

    Given ten tasks, five trials each, and a fixed budget of model calls.

    Evidence a results table with success in every trial, success in any trial and cost per completed task.

  6. Performance

    Decide between two configurations using a paired comparison with its uncertainty, cost and latency.

    Given the evaluation suite and a stated minimum effect of interest.

    Evidence a one-page decision memo that a reviewer can re-run.

  7. Performance

    Build a regression gate that blocks a change when a critical failure mode gets worse.

    Given a repository with continuous integration.

    Evidence a pipeline run that passes on the baseline and fails on a seeded regression, with logs.

Topics

Evaluation as specification

  • Non-determinism and the gap between intent and behaviour
  • Benchmarks versus application evaluations
  • What a leaderboard does not tell you

Error analysis

  • Sampling traces
  • Open and axial coding
  • Failure taxonomies and saturation
  • Prioritising by frequency and severity

Evaluators

  • Assertions and reference-based checks
  • Binary criteria for model graders
  • Calibration against human labels
  • Correcting pass rates for grader error

Agents and retrieval

  • Grading transcript and outcome
  • Consistency over repeated trials
  • Groundedness and citation checks
  • Arabic test sets

Comparing and deciding

  • Paired comparisons and bootstrap intervals
  • Sample size and minimum effect
  • Cost, latency and quality as one decision

Evaluation in delivery

  • Golden sets and leakage
  • Regression gates
  • Online monitoring and review queues
  • Privacy of traces

Day by day

Four sessions a day. Each session presents the concepts with a demonstration, then ends in a lab.

#SessionLab
Day 1 See the failures
1.1Evaluation is the specificationRun the case assistant on 20 inputs and record what goes wrong in your own words
1.2Traces are the raw materialInstrument the assistant and export 100 traces to a table
1.3Open codingCode 50 traces and compare labels with a neighbour
1.4From codes to a failure taxonomyMerge codes into five or more failure modes with definitions and counts
Day 2 Build the instruments
2.1Checks you can write in codeWrite three assertions for structure and policy rules and run them over the traces
2.2Grounding and citation checksAdd a groundedness check for retrieved answers, including Arabic sources
2.3Model graders with binary criteriaWrite one grader prompt for a single failure mode and test it on 20 labelled examples
2.4Calibrating a grader against peopleMeasure true-positive and true-negative rates on a held-out set and correct the observed pass rate
Day 3 Agents and comparisons
3.1Grading a transcript and an outcomeScore five agent runs for outcome and for one process rule
3.2Consistency over repeated trialsRun ten tasks five times each and compute success in every trial and in any trial
3.3Is B better than ACompare two configurations with a paired bootstrap and report the interval
3.4Cost and latency belong in the decisionAdd cost per completed task and latency percentiles to the comparison table
Day 4 Gate the release
4.1Golden sets, versions and leakageFreeze a golden set with a version and check it for overlap with prompt examples
4.2A regression gate in continuous integrationAdd the suite to the pipeline and make a seeded regression fail the build
4.3From offline suites to online monitoringDefine three online signals and a review queue for the case assistant
4.4Reporting results people can act onDraft the decision memo and choose the capstone application

Statistics
SciPy, statsmodels
Continuous integration
GitHub Actions, GitLab CI

How the work is assessed

  • Supervised entry and exit checks of fundamentals without AI assistance (20%)
  • Capstone repository scored on a five-criterion rubric: working suite 25, error analysis 25, calibration and statistics 20, release gate 20, reproducibility 10 (60%)
  • Live defence of one design decision (20%)
To pass
70% overall and at least 60% on the capstone rubric

Use of AI in the course

AI-off for the supervised checks. AI-tutor in the labs: the course assistant hints one step at a time and does not write the evaluator. AI-full in the capstone, which the participant defends live.

AI-off: no AI assistance. AI-tutor: an assistant that hints and explains but does not give the answer. AI-full: any assistance; the participant owns the result and defends it.
