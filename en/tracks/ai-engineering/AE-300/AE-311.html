AE-311 Shaping the Build: Product Sense and Delivery Practice

  • Level 300 · Develop
  • Intensive
  • 21 h
  • Audience: practitioner

Track

AI Engineering

Stream

AE-300 AI Engineering: courses that help prepare for the Associate level

Level

Level 300 · Develop

Audience

practitioner

Format

Intensive: 3 teaching days of four sessions and a capstone day, with guided pre-work and a tracked follow-up task

Total hours

21 h

Prerequisites

  • AE-203 Building Applications on Language Models
  • AE-204 Software Engineering with Coding Agents
  • Has built and demonstrated a working language model application
  • Writes a short technical document for a non-technical reader

Badge

Helps prepare for the SDAIA AI Engineering badge, Associate level.

Description

Participants practise the engineer's part in deciding what to build. In a role-played engagement with a fictional regional water utility that asks for an AI assistant for leak reports, they interview call-centre and field staff about what happened last week, map the workflow and its exceptions, choose and reject use cases, write the specification as the main deliverable with acceptance criteria as evaluation cases, test the riskiest assumption with a thin prototype built with a coding agent, cost the value case, brief the utility's leadership and hand over a system the utility's own team can run.

Learning outcomes

By the end, the participant can:

  1. Applied

    Analyse a requested AI use case through interviews about past behaviour and a workflow map, and restate the problem where the evidence differs from the request.

    Given the utility's request memo and two role-played staff interviews.

    Evidence interview notes, a workflow map with exceptions and a one-paragraph problem statement.

  2. Applied

    Draft a specification with users, non-goals, constraints, data classification and acceptance criteria written as evaluation cases.

    Given the chosen use case.

    Evidence a specification another engineer can build from, with at least ten Arabic and English evaluation cases including escalations.

  3. Applied

    Test the riskiest assumption with a thin prototype and role-played user sessions.

    Given a coding agent, a free model and the evaluation cases.

    Evidence a prototype repository, session notes and a go, change or stop finding.

  4. Performance

    Build a value case with cost per successful task, ranges for uncertain inputs and a break-even point, and decide whether to proceed.

    Given the utility's report volumes, staff costs and model prices.

    Evidence a value model and a decision with its stated assumptions.

  5. Performance

    Deliver a recommendation and a hand-over package to non-technical leadership and the receiving team.

    Given a ten-minute slot before a role-played leadership panel.

    Evidence a hand-over pack with runbook, evaluation set, owners and exit criteria, and answers to the panel's questions.

Topics

Discovery

  • Interviews about past behaviour
  • Workflows and their exceptions
  • Choosing and rejecting use cases

Specification as the deliverable

  • Problem, users and non-goals
  • Acceptance criteria as evaluation cases
  • Data, permissions and classification

Minimum viable decisions

  • Riskiest assumption first
  • Reversible and irreversible choices
  • Decision records

Value and communication

  • Cost per successful task and break-even
  • Ranges instead of point estimates
  • Updates for leaders
  • Saying what the system cannot do

Hand-over

  • Runbooks and evaluation sets
  • Ownership and exit criteria
  • Training the receiving team

Day by day

Four sessions a day. Each session presents the concepts with a demonstration, then ends in a lab.

#SessionLab
Day 1 Discover
1.1The engineer's job before codeRead the utility's request memo and list the assumptions it hides
1.2Interviews about past behaviourInterview a role-played call-centre agent and field supervisor about last week's reports
1.3Workflows and their exceptionsMap the leak-report workflow with hand-offs and exceptions and mark where AI could help or harm
1.4Choosing the problemScore three candidate use cases on value, feasibility, data and risk, and write why one is rejected
Day 2 Specify and test
2.1Specification as the deliverableWrite the problem, users, non-goals and constraints for the chosen use case
2.2Acceptance criteria as evaluation casesTurn the criteria into ten Arabic and English cases, including ones the system must escalate
2.3Data, permissions and classificationClassify each data item the system touches and record what may leave the utility

Day 3 Decide, communicate and hand over
3.1Minimum viable decisionsSort five design decisions into reversible and irreversible and write a decision record for one
3.2The value caseCost the value case with cost per successful task, ranges and a break-even point
3.3Talking to leadersWrite a one-page update for the utility's director stating what works, what does not and the ask
3.4Hand-overDraft the runbook, owners and exit criteria for the supplied prototype, then choose the capstone engagement

Tools and platforms

These are examples. Any equivalent tool may be used instead.

Coding agent
OpenCode, goose, any commercial coding agent the data rules allow
Language model access
a locally served open-weight model, any commercial API
Workflow mapping
Excalidraw, bpmn.io
Value modelling
a spreadsheet, a Python notebook
Specifications and decision records
Markdown files in the repository, any team wiki

How the work is assessed

  • Supervised check without AI assistance: critique a flawed specification and compute a small value case (20%)
  • Capstone package on a five-criterion rubric: problem framing 20, specification and evaluation cases 25, prototype evidence 15, value case 20, hand-over 20 (60%)
  • Live recommendation and questions (20%)
To pass
70% overall and at least 60% on the capstone rubric

Use of AI in the course

AI-off for the interviews, the supervised check and the first problem statement. AI-tutor when drafting the specification: the assistant questions gaps but does not write it. AI-full for the prototype, which the participant explains and defends.

AI-off: no AI assistance. AI-tutor: an assistant that hints and explains but does not give the answer. AI-full: any assistance; the participant owns the result and defends it.
