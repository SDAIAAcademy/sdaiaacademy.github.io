AE-308 Securing Language Model and Agent Applications

Level

Audience

Format

Intensive: 4 teaching days of four sessions and a capstone day, with guided pre-work and a tracked follow-up task

Total hours

Prerequisites

  • AE-207 Responsible and Secure AI Engineering Practice
  • AE-302 Agentic Systems Engineering: Loops, Context and Harnesses
  • Has built a tool-calling agent and read its traces
  • Runs containers locally and changes their network settings

Badge

Helps prepare for the SDAIA AI Engineering badge, Associate level.

Description

Participants attack and then defend a working agent: a synthetic clearance assistant for a fictional port authority that reads importers' emails and invoices, searches a tariff knowledge base, remembers each importer, runs code to compute duties and acts through Model Context Protocol (MCP) servers. They threat-model it, run injection, exfiltration and poisoning attacks over repeated trials, then contain it with a sandbox and egress rules, scoped short-lived delegated tokens, separated privileged and quarantined model calls, measured guardrails and approvals placed where a person adds safety. Red-team programmes are AE-407.

Learning outcomes

By the end, the participant can:

  1. Applied

    Prepare a threat model with data flows, trust boundaries and threats mapped to recognised risk lists and adversary-technique catalogues.

    Given the clearance agent, its tool list and the classification of its data.

    Evidence a threat model with at least 12 threats, each mapped and scored on the national four-by-four likelihood and impact scale.

  2. Applied

    Test the application with direct, indirect, memory and tool-poisoning attacks in Arabic and English over repeated trials.

    Given a starter attack corpus and a fixed budget of model calls.

    Evidence an attack log with a success rate and interval for each technique.

  3. Performance

    Design containment for generated code and outbound actions with a sandbox, an egress allowlist and recipient rules.

    Given the attack log and 50 benign tasks.

    Evidence a rerun in which every logged exfiltration path fails while at least 95% of benign tasks still pass.

  4. Performance

    Build delegated authorisation in which each tool call carries an exchanged token with one audience, a narrow scope and a short lifetime.

    Given two protocol servers that share one API key and a containerised identity provider.

    Evidence a token audit and a confused-deputy test that fails against the hardened design.

  5. Applied

    Configure input guardrails and output validation and measure their false-positive and false-negative rates.

    Given bilingual attack and benign sets.

    Evidence a tuning report with the chosen thresholds and both error rates.

  6. Performance

    Defend a residual-risk statement after another team attacks the hardened agent, with each confirmed finding turned into a regression test.

    Given a timed red-team exercise.

    Evidence a findings report keyed to risk-list entries, a passing regression suite and a live defence.

Topics

Threat modelling agents

  • Data-flow diagrams and trust boundaries
  • Private data, untrusted content and exit paths
  • Model as component versus model as actor
  • Risk lists, technique catalogues and scoring

Attacks

  • Direct, indirect and cross-modal injection
  • Exfiltration through links, tool arguments and permitted paths
  • Memory, retrieval and tool poisoning
  • Success rates over repeated trials

Containment

  • Sandboxes for generated code
  • An egress allowlist is a capability grant
  • Read-only mounts and resolving links before path checks
  • Privileged and quarantined model calls

Identity and authorisation

  • OAuth-based delegation and token exchange
  • Audience, scope and lifetime
  • Token passthrough and the confused deputy
  • Credentials kept outside the agent's reach

Guardrails, approvals and audit

  • Classifiers and their two error rates
  • Schema and policy checks on tool arguments
  • Approval fatigue and where a person adds safety
  • Rate limits, spend caps and a kill switch
  • Action logs and security regression suites

Day by day

Four sessions a day. Each session presents the concepts with a demonstration, then ends in a lab.

#SessionLab
Day 1 Model the threats
1.1A fooled model must break nothing importantRun the agent on ten tasks and list every entry point for untrusted text and every action it can take
1.2Data flows and trust boundariesDraw the data-flow diagram and mark private data, untrusted content and exit paths
1.3Risk lists and technique cataloguesMap ten threats to OWASP risk entries and MITRE ATLAS techniques
1.4Scoring and choosing what to testScore the threats on the national likelihood and impact scale and pick five to attack
Day 2 Attack
2.1Direct and indirect injectionInject through an importer email and a poisoned invoice, ten trials each, and record success rates
2.2Exfiltration pathsLeak a synthetic importer record through a rendered link, a tool argument and the permitted email tool
2.3Memory and retrieval poisoningPlant an instruction in the knowledge base and in importer memory and trigger it in a later session
2.4Hostile toolsChange a protocol server's tool description after approval, observe the agent, then pin approved descriptions by hash
Day 3 Contain
3.1Sandboxes for generated codeRun the duty-calculation tool with no network and read-only mounts, then fix a symbolic-link escape
3.2Egress rules as capability grantsAllow only the case-system host, show that email still leaks data, then close it with recipient rules
3.3Delegated authorisationReplace the shared API key with exchanged, audience-bound short-lived tokens across two servers
3.4Privileged and quarantined callsSplit the agent so the model that reads invoices cannot call tools, and rerun the supplied attacks
Day 4 Guard, approve and verify
4.1Guardrails and their error ratesTune an input classifier on bilingual attack and benign sets and report both error rates
4.2Validating outputs and tool argumentsCheck tool arguments against schemas and policy rules and escape model output before rendering
4.3Approvals that people can judgePlace one approval on outbound email, design what the approver sees and count approvals over 50 tasks
4.4Audit logs and regression suitesTurn three supplied attacks into a regression suite in continuous integration, then choose the capstone target

Tools and platforms

These are examples. Any equivalent tool may be used instead.

Attack tooling

Tracing and audit
OpenTelemetry with Jaeger, Langfuse
Risk and technique references
OWASP GenAI Security Project lists and testing guide, MITRE ATLAS

How the work is assessed

  • Supervised entry and exit checks without AI assistance on an unseen architecture diagram (20%)
  • Capstone repository on a five-criterion rubric: threat model 20, attack evidence 20, containment and authorisation 30, guardrails and approvals 15, regression suite and report 15 (60%)
  • Live defence of the residual-risk statement (20%)
To pass
70% overall and at least 60% on the capstone rubric

Use of AI in the course

AI-off for the supervised checks and the first threat model. AI-tutor in the labs: the assistant explains attacks and controls but does not write configuration. AI-full on the red-team day and in the capstone, including attacker models, with prompts logged and the result defended live.

AI-off: no AI assistance. AI-tutor: an assistant that hints and explains but does not give the answer. AI-full: any assistance; the participant owns the result and defends it.
