SPC-RSP-404 Frontier Seminar: Neurosymbolic Methods and AI for Mathematics

  • Level 400 · Evaluate
  • Seminar
  • 24 h
  • Audience: specialist

Track

Data Science

Stream

SPC-RSP Research Practice and Frontier

Level

Level 400 · Evaluate

Audience

specialist

Format

Seminar: six weekly sessions of reading, presentation and hands-on work with solvers, verifiers and proof assistants, rebuilt each term from current conference tutorials

Total hours

24 h

Prerequisites

  • Writes proofs at the level of a discrete mathematics course, as in FND-MTH-105, or equivalent
  • Has used search, logic or constraint solving, as in FND-AIC-105, or equivalent
  • Calls a language model API from Python and parses structured output
  • No proof-assistant experience is assumed; the tracked pre-work introduces one

Description

A reading and hands-on seminar on systems that combine learned models with symbolic tools: language models that call solvers, generated programs checked by verifiers, and proofs checked by a proof assistant. Each week participants read current papers and run a small experiment: proving lemmas with a model, verifying generated code against formal specifications, solving constraint problems with a model plus a solver, and checking whether autoformalised statements say what the informal ones say.

Learning outcomes

By the end, the participant can:

  1. Awareness

    Explain the main neurosymbolic patterns: a model proposes and a solver checks, a model guides search, differentiable logic, and learned heuristics inside solvers.

    Given the term's reading list.

    Evidence a pattern map with one example paper for each pattern, presented in session.

  2. Applied

    Use a language model with a proof assistant to prove a set of small lemmas and report success over repeated attempts.

    Given a set of formal statements and an open-weight prover model.

    Evidence a run log with verified proofs and success rates over a stated number of attempts.

  3. Performance

    Build a generate-and-verify loop that writes code with a formal specification and rejects any output the verifier does not accept.

    Given five programming tasks and a verification-aware language.

    Evidence a repository with specifications, verified programs and a log of rejected attempts.

  4. Performance

    Evaluate the faithfulness of autoformalised statements against their informal originals.

    Given twenty statements formalised by a model.

    Evidence an audit table classifying each statement as faithful, weaker, stronger or wrong, with reasons.

  5. Performance

    Review a neurosymbolic or AI-for-mathematics paper for what its verification guarantees, its contamination risk and its compute budget.

    Given a paper the participant presents.

    Evidence a presentation and written critique scored on a rubric.

Topics

Neurosymbolic patterns

  • Model proposes, solver or verifier checks
  • Learned guidance for search and solvers
  • Differentiable and probabilistic logic

Theorem proving and autoformalisation

  • Tactic prediction versus whole-proof generation
  • Reinforcement learning from verifier feedback
  • Misformalisation and human review of statements
  • Benchmarks, contamination and success over attempts

Verified code generation

  • Specifications, pre- and postconditions, invariants
  • Solver-backed verification-aware languages
  • Property-based testing as a weaker check
  • What a verified program still does not guarantee

AI and mathematical research

  • Recorded AI contributions to open problems and how they were checked
  • Credit and disclosure of AI contributions

Tools and platforms

These are examples. Any equivalent tool may be used instead.

Proof assistant with a mathematics library
Lean with Mathlib, Isabelle with the Archive of Formal Proofs
Verification-aware programming language
Dafny, Why3, Verus
Satisfiability modulo theories and constraint solvers
Z3, cvc5, MiniZinc
Property-based testing
Hypothesis, QuickCheck
Language model access
an open-weight prover or code model served with vLLM or llama.cpp, a hosted model through a standard chat-completion API

How the work is assessed

  • Supervised short check on reading specifications and proofs, without AI (10%)
  • Paper presentation and written critique (25%)
  • Lab logs and repositories (40%)
  • Extension note and presentation (25%)
To pass
70% overall with no component below 50%

Use of AI in the course

AI-off in the supervised check and when writing a first specification by hand. AI-full in the proving and code-generation labs, which study model assistance; the verifier, not the participant's trust in the model, decides acceptance.

AI-off: no AI assistance. AI-tutor: an assistant that hints and explains but does not give the answer. AI-full: any assistance; the participant owns the result and defends it.
