FND-PRG-104 Software Testing, Code Review and Documentation

  • Level 100 · Explain
  • Intensive
  • 30 h
  • Audience: beginner

Track

Data & AI Foundations

Stream

FND-PRG Programming and Software Practice

Level

Level 100 · Explain

Audience

beginner

Format

Intensive: 4 teaching days and a capstone day, with guided pre-work and a tracked follow-up task

Total hours

30 h

Prerequisites

  • FND-PRG-101 Python Programming for Data and AI
  • FND-PRG-102 Command Line, Git and Reproducible Environments

Description

Participants take a small, untested data-cleaning library and make it trustworthy. They write unit and integration tests, design cases from a specification, isolate files, time and network calls with fixtures and test doubles, review each other's pull requests against a checklist, write a README and reference documentation, and package the library so it installs and passes its tests in a clean environment. Property and mutation testing and the verification of agent-written code follow in DEV-SWE-204.

Learning outcomes

By the end, the participant can:

  1. Awareness

    Distinguish unit, integration and end-to-end tests, and explain what each can and cannot show.

    Given a data pipeline with five reported defects.

    Evidence each defect assigned to the cheapest test level that catches it, correct for four of five.

  2. Applied

    Design test cases from a specification using equivalence partitions, boundary values and error cases.

    Given a specification for normalising dates and Arabic and English names.

    Evidence cases traced to the specification's rules that expose two of three seeded defects.

  3. Applied

    Implement unit and integration tests with fixtures and test doubles for files, time and network calls.

    Given the untested library and a fake web service.

    Evidence a suite that passes on a clean checkout in under a minute and reports coverage.

  4. Applied

    Review a pull request for correctness, tests, readability and security, and write actionable comments.

    Given two pull requests with seeded issues, one written by a colleague and one by an assistant.

    Evidence comments that find at least four of six seeded issues, each with a suggested fix.

  5. Applied

    Prepare a README and reference documentation, and package the library for installation.

    Given the tested library and a standard project metadata file.

    Evidence a package that installs and passes its tests in a fresh environment, with a README a peer follows unaided.

  6. Performance

    Deliver a tested, reviewed and documented release with automated checks on every change.

    Given a repository with continuous integration (CI).

    Evidence a tagged release, a CI run that fails on a seeded regression, and a short defence.

Topics

What to test

  • Tests as executable specification
  • Test levels and their costs
  • What coverage hides

Designing tests

  • Partitions and boundary values
  • Empty, missing and mixed-script text
  • Regression tests from bug reports

Test tooling

  • Fixtures and parametrised tests
  • Test doubles for files, time and network
  • Tests in CI on each pull request

Code review

  • Checklists and small pull requests
  • Giving and receiving comments
  • Assistant-generated code held to the same standard

Documentation and packaging

  • README and quick start
  • Docstrings and generated reference pages
  • Semantic versioning and a change log
  • Building and installing a package

Tools and platforms

These are examples. Any equivalent tool may be used instead.

Test runner and coverage
pytest with coverage.py, unittest
Documentation generator
Sphinx, pdoc
Package build to the standard metadata format
uv build, python -m build
Continuous integration
Forgejo Actions, GitLab CI, GitHub Actions

How the work is assessed

  • Supervised AI-off test-design check (20%)
  • Labs (30%)
  • Capstone release on a rubric (35%)
  • Live defence (15%)
To pass
65% overall, at least 60% on the supervised check, and a passed defence

Use of AI in the course

AI-off for the first tests in each lab and the supervised check. AI-tutor for test ideas and documentation feedback. AI-full for the capstone, where generated code must pass review and be explained in the defence.

AI-off: no AI assistance. AI-tutor: an assistant that hints and explains but does not give the answer. AI-full: any assistance; the participant owns the result and defends it.
