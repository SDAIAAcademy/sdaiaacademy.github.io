Prerequisites

  • Has written and run a short program in any language, or completed the guided pre-work on values, conditions and loops

Description

Participants write Python the way data and AI work needs it: small typed functions over collections and files, errors that fail loudly, and code moved out of notebooks into scripts that rerun. The case is a fictional regional water utility with synthetic meter readings in comma-separated values (CSV) files and bilingual service tickets in JavaScript Object Notation (JSON) Lines. Each day opens with an AI-off drill in reading, tracing or debugging code by hand, and the labs grow into a command-line tool that validates readings, flags anomalies and writes a summary report. Arabic text normalisation and SQL are left to FN-104, version control to FN-102.

Learning outcomes

By the end, the participant can:

  1. Awareness

    Explain what a short program prints, step by step, including name binding, shared mutable lists and dictionaries, and scope.

    Given ten unseen snippets on paper, without a computer or assistant.

    Evidence a trace sheet with at least eight of ten outputs correct.

  2. Awareness

    Distinguish when a notebook, a script or an importable module is the right home for a piece of code.

    Given four tasks described by the utility's analysts.

    Evidence a choice and a one-line reason per task, matching the reference on three of four.

  3. Applied

    Implement typed functions that load, validate and aggregate records with lists, dictionaries, sets and comprehensions.

    Given a month of meter readings with missing, duplicated and out-of-range values.

    Evidence a module that passes the provided tests and a type checker with no errors.

  4. Applied

    Apply exception handling and input validation so that each bad record is reported with a reason instead of crashing or passing silently.

    Given a ticket file with malformed lines, mixed Arabic and English text and a wrong encoding.

    Evidence a rejection log that accounts for every input line.

  5. Applied

    Use a repeatable debugging method: reproduce, shrink the input, form a hypothesis, test it, fix, and add a regression check.

    Given three seeded defects in the course codebase, with AI assistance off.

    Evidence a debugging log per defect and a passing regression test for each.

  6. Applied

    Prepare a command-line tool from an exploratory notebook, with an entry point, arguments and a written report.

    Given the utility's analysis notebook and raw files.

    Evidence a script that rebuilds the same report from raw files with one command on two runs.

Topics

Reading and tracing code

  • Values, names and references
  • Mutation and aliasing
  • Scope and the call stack
  • Predict-the-output and Parsons problems

Functions and types

  • Decomposing a task into small functions
  • Type hints and a type checker
  • Docstrings and doctests
  • Modules and the standard library

Collections for data

  • Lists, tuples, dictionaries and sets
  • Comprehensions and generators
  • Sorting with keys, counting and grouping
  • Data classes for records

Files, text and errors

  • CSV and JSON Lines
  • Bytes, UTF-8 and decoding errors, with Arabic examples
  • Exceptions that explain
  • Reading tracebacks

From notebook to tool

  • Hidden state in notebooks
  • Entry points and arguments
  • Logging instead of print
  • Assistants as tutors, not authors

Day by day

Four sessions a day. Each session presents the concepts with a demonstration, then ends in a lab.

#SessionLab
Day 1 Read before you write
1.1Values, names and referencesTrace eight snippets on paper, then check each answer in a step visualiser
1.2Functions with clear contractsSplit a 40-line script into four functions with stated inputs and outputs
1.3Type hints and a checkerAnnotate the supplied reading parser and fix every error the type checker reports
1.4Parsons problemsReorder scrambled lines, with distractors, into a working validation function
Day 2 Collections for data work
2.1Dictionaries for counting and groupingCount readings per meter and district, then time a nested-loop version on 100,000 rows
2.2Sets and membershipFind meters with no reading and readings with no known meter
2.3Comprehensions and generatorsStream a large readings file with a generator and compare peak memory with a list
2.4Records as data classesModel a ticket as a data class and sort tickets by priority and age
Day 3 Files, text and failure
3.1CSV and JSON LinesLoad readings and tickets and write a JSON summary per district, masking phone numbers before anything is written
3.2Text, bytes and encodingsOpen a ticket file that fails to decode, read it with the declared encoding and list the lines that still fail
3.3Exceptions that explainReject malformed lines with a reason code so every input line is accounted for
3.4A debugging methodWith AI off, find and fix two seeded defects and write a regression test for each
Day 4 From notebook to tool
4.1What notebooks hideRun a notebook out of order, find the hidden-state bug, then restart and run all
4.2Scripts, modules and an entry pointMove the supplied notebook logic into a module with a command-line entry point
4.3Tests as a safety netWrite five tests for the anomaly rule, including empty and boundary inputs
4.4Learning with an assistant without losing the skillGet hints from the course tutor on a new defect, then explain the fix in your own words

How the work is assessed

  • Supervised AI-off check: tracing, a Parsons problem and one debugging task in a locked editor (30%)
  • Capstone repository on a five-criterion rubric: correctness on hidden tests 30, validation and errors 20, structure and types 20, reproducibility 15, README 15 (50%)
  • Live walkthrough with a requested change (20%)
To pass
70% overall and at least 60% on the AI-off check

Use of AI in the course

AI-off for the daily drills, the first attempt at each debugging lab and the supervised check. AI-tutor in the other labs, set by the course repository's agent instructions to give hints, not code. AI-full in the capstone, which the participant walks through and changes live.

AI-off: no AI assistance. AI-tutor: an assistant that hints and explains but does not give the answer. AI-full: any assistance; the participant owns the result and defends it.
