FN-102 Command Line, Git and Reproducible Projects

  • Level 100 · Explain
  • Intensive
  • 21 h
  • Audience: beginner

Track

Data & AI Foundations

Stream

FN-100 Shared Foundations: the entry courses for both badge tracks

Level

Level 100 · Explain

Audience

beginner

Format

Intensive: 3 teaching days of four sessions and a capstone day, with guided pre-work and a tracked follow-up task

Total hours

21 h

Prerequisites

  • FN-101 Python for Data and AI Work
  • Opens a terminal and runs a Python script with arguments

Description

Participants take a working but fragile analysis project and make it something another person can rebuild, review and trust. The case is a fictional public library network whose monthly loans report sits in one folder with hard-coded paths, no history, unpinned packages and a key in a configuration file. Over three days they script the shell, put the project under version control, review and merge through pull requests, lock the environment, add tests that run on every push, and write a README that reports measured results. A peer then rebuilds it on a clean machine.

Learning outcomes

By the end, the participant can:

  1. Awareness

    Explain what a commit, a branch, a merge and a pull request record, and how each can be undone safely.

    Given a printed history graph of a shared repository and three described mistakes.

    Evidence an annotated graph naming the commit to restore and the command to use for each mistake.

  2. Awareness

    Identify where secrets, personal data, large outputs and machine-specific paths leak into a project.

    Given a seeded repository.

    Evidence a findings list that matches at least five of six seeded problems, with the fix for each.

  3. Applied

    Use shell pipelines, redirection and exit codes to inspect and summarise files without writing a program.

    Given a folder of synthetic loan logs.

    Evidence a script of five commands whose outputs match the reference counts.

  4. Applied

    Use branches, pull requests and review comments to integrate a change, resolving a merge conflict without losing either side's work.

    Given a shared repository worked on in teams of three.

    Evidence a merged pull request with review comments answered and a readable history.

  5. Applied

    Configure a project environment with declared dependencies and a lock file so that it installs identically on a clean machine.

    Given the library project with unpinned packages.

    Evidence a lock file and an install log from a second machine that runs the report unchanged.

  6. Applied

    Implement tests that run in continuous integration and a README that reports measured results with the command that produced them.

    Given the report's calculation functions.

    Evidence a passing pipeline, a failing run on a seeded defect, and a README a peer follows to reproduce the same numbers.

Topics

The shell

  • Paths, permissions and environment variables
  • Pipes, redirection and filters
  • Exit codes and short scripts
  • Remote login with secure shell (SSH) keys

Version control and review

  • Commits, staging and history
  • Branches, merges and conflicts
  • Pull requests and review etiquette
  • Undoing mistakes without rewriting shared history

Reproducible environments

  • Virtual environments
  • Declared dependencies and lock files
  • Pinned interpreter versions
  • Data and outputs kept outside the code

Tests and continuous integration

  • Unit tests for calculations
  • Small synthetic test data
  • A pipeline that runs on every push

Hygiene and reporting

  • Secrets out of history: rotate, then clean
  • Ignore files and pre-commit hooks
  • A README that reports results
  • A change log and a tagged release

Day by day

Four sessions a day. Each session presents the concepts with a demonstration, then ends in a lab.

#SessionLab
Day 1 Shell and history
1.1Working in the shellNavigate a project tree and fix three seeded path and permission faults
1.2Pipelines over textCount loans per branch and month from raw logs, one pipeline per question
1.3First commitsPut the library project under version control with an ignore file and five small commits
1.4Reading and undoing historyRecover a deleted function and revert a bad commit on a supplied repository
Day 2 Collaborate and lock
2.1Branches and pull requestsOpen a pull request that adds an overdue-rate metric and answer two review comments
2.2Merge conflictsIn teams of three, resolve a seeded conflict so that both changes survive
2.3Environments and lock filesLock the dependencies and rebuild the environment from nothing in a fresh folder
2.4Secrets and large filesFind a seeded key and a data dump in history, rotate the key and remove both
Day 3 Test, automate, report
3.1Tests for calculationsWrite tests for the loan-rate functions, including an empty month
3.2Continuous integrationAdd a pipeline that installs from the lock file and runs the tests on every push
3.3A README that reports resultsWrite the rebuild steps and a results table produced by one command
3.4Reproduction from a READMERebuild a supplied project from its README alone on a clean workspace and file an issue for each failed step

Tools and platforms

These are examples. Any equivalent tool may be used instead.

Version control and hosting
Git with Forgejo or Gitea, Git with GitLab or GitHub
Shell
Bash or Zsh, Git Bash or a Linux subsystem on Windows
Environment and lock-file manager
uv, Poetry, pip-tools
Test runner
pytest, unittest
Continuous integration
Forgejo Actions, GitLab CI, GitHub Actions
Secret scanning and hooks
gitleaks with pre-commit, the host's built-in secret scanning

How the work is assessed

  • Supervised AI-off check: shell and version-control tasks in a sandboxed terminal and a history graph to read (30%)
  • Capstone repository: peer reproduction 30, history and review 20, tests and continuous integration 25, README with measured results 25 (50%)
  • Live defence with an undo and a conflict on request (20%)
To pass
70% overall, at least 60% on the AI-off check, and a peer reproduction that succeeds after at most one round of fixes

Use of AI in the course

AI-off for the supervised check and the first attempt at the history and conflict labs. AI-tutor in the other labs, explaining commands rather than running them. AI-full in the capstone, provided the participant can perform any step live.

AI-off: no AI assistance. AI-tutor: an assistant that hints and explains but does not give the answer. AI-full: any assistance; the participant owns the result and defends it.
