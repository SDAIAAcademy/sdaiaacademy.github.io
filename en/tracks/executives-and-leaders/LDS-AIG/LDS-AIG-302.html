LDS-AIG-302 Generative AI and Agent Controls Laboratory

  • Level 300 · Develop
  • Intensive
  • 24 h
  • Audience: specialist

Track

Executives & Leaders

Stream

LDS-AIG AI Governance, Risk and Assurance

Level

Level 300 · Develop

Audience

specialist

Format

Intensive: 3 teaching days and a capstone day, with guided pre-work and a tracked follow-up task

Total hours

24 h

Prerequisites

  • LDS-AIG-201 AI Governance Foundations: Principles, Roles and Lifecycle Controls
  • Uses a terminal to run provided commands and edits YAML or JSON configuration files
  • Describes how a language model assistant calls tools and retrieves documents
  • Scores a risk by likelihood and impact against a stated appetite (LDS-AIG-204 or equivalent)

Description

In containerised labs on synthetic targets, participants configure and test the controls that make generative AI and agents governable: input and output guardrails, groundedness checks, sandboxes with egress limits, tool allow-lists and scoped credentials, approval gates, rate limits, a kill-switch and audit logging. They attack a provided staff helpdesk agent with open red-team tools, map findings to public risk lists and a threat knowledge base, harden the agent and assemble a control evidence pack for a risk committee. Cross-listed with DEV-SEC; building these controls into application code is DEV-SEC-301, and full red-team programmes are DEV-SEC-302.

Learning outcomes

By the end, the participant can:

  1. Awareness

    Identify the main risk classes of language model and agent applications and distinguish model-as-component risks from model-as-actor risks.

    Given ten incident descriptions.

    Evidence a mapping of each incident to an entry in the public risk lists, with at least eight of ten correct.

  2. Applied

    Configure input and output guardrails, groundedness checks and content filters, and measure their effect on blocked attacks and false refusals.

    Given a provided assistant, an attack set and a benign request set.

    Evidence a before-and-after table of attack success and false refusal rates.

  3. Applied

    Configure an agent sandbox with tool allow-lists, scoped credentials, egress limits, rate limits, human approval for high-impact actions and a kill-switch.

    Given a staff helpdesk agent with email, file and ticketing tools on synthetic data.

    Evidence a configuration file and a test run showing each control blocking its target action.

  4. Applied

    Implement audit logging of prompts, retrieved content, tool calls, approvals and policy decisions, with filtering of personal data.

    Given the agent and a trace store.

    Evidence a log extract from which a reviewer reconstructs one incident end to end without seeing personal data.

  5. Performance

    Design and run a red-team exercise against an agent, with scope, rules of engagement, attack scenarios and severity scoring.

    Given the helpdesk agent and open red-team tools.

    Evidence a findings report with reproduction steps, each finding mapped to a public risk entry and a threat technique.

  6. Performance

    Evaluate whether the hardened agent's residual risk is acceptable for its risk level and assemble the control evidence pack.

    Given red-team results before and after hardening and the agent's risk level.

    Evidence an evidence pack and a residual-risk recommendation defended live.

Topics

Threat model for generative systems

  • Untrusted input everywhere: direct, indirect and cross-modal prompt injection
  • Poisoned retrieval content and agent memory
  • Model as component versus model as actor
  • Public risk lists for language model and agentic applications
  • Threat knowledge bases of adversary tactics and techniques

Guardrails

  • Input and output filters
  • Safety classifiers and their error rates
  • Groundedness and citation checks
  • Structured output validation
  • False refusals as a cost

Agent containment

  • Sandboxes and egress control
  • Tool allow-lists, agent identity and scoped credentials
  • Memory boundaries
  • Approval gates for high-impact actions
  • Rate limits, budgets and kill-switches

Tool servers and connectors

  • What a tool server can reach
  • Reviewing tool descriptions for poisoning
  • Least privilege for connectors

Red teaming

  • Scope and rules of engagement
  • Manual and automated probing
  • Scoring severity and likelihood
  • Turning findings into regression tests

Logging and evidence for audit

  • What to log and what not to log
  • Trace schemas and retention
  • Reconstructing an incident
  • Control evidence packs and residual-risk sign-off

Tools and platforms

These are examples. Any equivalent tool may be used instead.

Container runtime with network egress control
Podman, Docker
Locally served open-weight models
Ollama, vLLM, llama.cpp
Guardrail and policy layer
an open-source guardrail framework, an open-weight safety classifier model, Open Policy Agent for tool-call policies
Red-team and probing tools
garak, PyRIT, promptfoo, Inspect
Tool protocol
Model Context Protocol servers, plain function-calling tools
Trace store and viewer
OpenTelemetry traces with a notebook viewer, Langfuse, Arize Phoenix
Risk and threat references
OWASP GenAI Security Project lists for language model and agentic applications, with its AI testing guide, MITRE ATLAS

How the work is assessed

  • Supervised check without AI assistance: map attacks to risk classes and choose controls for an unseen agent design (20%)
  • Graded labs with configuration files and run logs (35%)
  • Capstone findings report and evidence pack (35%)
  • Live defence (10%)
To pass
70% overall, at least 60% on the supervised check and on the capstone, and no critical finding left unreported in the capstone

Use of AI in the course

AI-off for the supervised check. AI-tutor in the labs, limited to explaining tool output and configuration syntax. AI-full for generating attack variants and drafting the evidence pack, with every finding reproduced by the participant.

AI-off: no AI assistance. AI-tutor: an assistant that hints and explains but does not give the answer. AI-full: any assistance; the participant owns the result and defends it.
